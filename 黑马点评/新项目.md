2. **使用 Caffeine + Redis 两级缓存(活动信息和商品列表走两级缓存, 库存单独走Redis)**
	1. 会使用 refreshAfterWrite 进行更新Caffeine的数据, 它适用于 持续高并发读 这个场景, 数据延迟就是刷新的间隔. 
	   ```
为什么适用这个更新策略呢?
	因为秒杀就是流量密集并且集中, 热点key的访问频率高, 保证 refreshAfterWrite一定能被触发
	   ```
	2. Caffeine底层有冷加载(硬过期时间)和热加载(刷新间隔). 
		1. 冷加载就是超过了设定时间像1个小时, 数据被删除, 下次到来的访问走(Redis->Dubbo回源)
		   ```
这里有两个防护, 缓存穿透和缓存击穿的防护
	缓存穿透: 如果Dubbo回源发现为null, 那么就给Reis中写入一个短ttl的null值, 下次有新访问直接返回. 同时Caffeine层用一个 `NULL_VALUE` 作为占位符(因为Caffeine不允许value为null)
	缓存击穿: 为了防止秒杀开始瞬间某个活动key失效了, 内置了只有一个线程允许去重置缓存, 其他等待.  但是因为我有refreshAfterWrite 刷新策略兜底, 所以一般数据不会过期, 走不到冷加载
		   ```
		2. 热加载就是超过了刷新间隔但是没有达到硬过期, 下次访问会立即返回旧值, 同时后台线程异步刷新(也就是refreshAfterWrite)(从Redis)
```
为什么选择Caffeine, 而不选择堆外缓存(Off-Heap Cache) 或者 Ehcache 3?
	OHC适合商品搜索, 推荐列表这类几十万甚至上百万条数据的场景
	Ehcache 3, 支持 堆内->堆外->磁盘的多级存储分层, 但是它比较OHC还重
	秒杀数据量小, 用本地缓存足矣
	所以选择方案时, 评估要缓存的数据量和对象的存活时间, 数据量可控就堆内, 数据量大就堆外
```

# ==秒杀系统的四层防刷体系==: 网关QPS限流(Sentinel(Gateway层))、机审校验(Service层)、用户级限流+小黑屋、消费端二次过滤
1. **网关层:** (总体限流)
	- 本项目中的主要执行顺序为: (过滤器直接通过 `chain.filter(exchange)` 去调用, 而不是HTTP)
```text
客户端请求
    ↓
TraceGatewayFilter（Order = -100）(链路追踪的)
生成或透传 traceId
    ↓
AuthGatewayFilter（Order = -50）(jwt鉴权的)
校验 JWT，注入可信 userId
    ↓
Sentinel 限流过滤器
    ↓
Gateway 路由转发过滤器
    ↓
下游服务
```

```
jwt鉴权流程: 

1. 获取请求路径
2. 判断路径是否在白名单
3. 从 Authorization 请求头获取 JWT
4. 检查是否以 Bearer 开头
5. 验证 JWT 签名和有效期
6. 从 JWT 中解析 userId
7. 删除客户端可能伪造的 X-User-Id
8. 注入网关验证后的 X-User-Id
9. 放行到后续过滤器
```
2. 机审校验(识别黄牛脚本)
```
请求顺序

1. 用户请求经过seckill-gateway，完成JWT鉴权和QPS限流
2. 请求转发到seckill-service
3. **机审校验**：比对预检令牌，过滤脚本请求
4. 用户级限流：Redisson RRateLimiter，防止单用户高频请求
5. 活动状态校验：通过两级缓存查活动是否在进行中
6. 限购校验、库存校验
7. 发送MQ消息，进入排队流程
```
- 作用就是: 用最小代价过滤掉最大比例的垃圾流量(前提是脚本绕过前端去直接去访问接口), 性价比高
- 实现: 分两步: 
	1. 用户进入秒杀界面后, 前端会调用一个预检接口, 然后服务端会生成一个16位的随机字母串和当前的时间戳, 对时间戳进行16取余然后在字母串对应的位置插入一个标记字符 `(eg: ABCD->AzCD, 这里的z就是通过时间戳算出来的位置)`, 得到校验值, 存入Redis(30s), 原始的随机字母串和时间戳返回给前端
	2. 前端拿到相关数据后, 用相同算法计算出校验值, 用户点击抢购时, 把算出来的校验值放在请求参数里带回来, 服务端从Redis取出之前存的校验值, 进行对比, 一致就放行, 同时用完即删
	对比流程: 三步: 检查key是否存在、比对值是否一致、通过后删除。
		`hasKey` + `get` + `delete` 是三次Redis操作，在极端高并发下是否存在竞态条件？
		
		存在的. 两个请求带同一个校验值都通过这种情况. 这种风险可以接收, 首先就是前端的抢购按钮
		点击后会变为loading, 用户无法发出两个请求; 其次脚本即使通过, 后面还有用户级限流和限购
		校验兜底, 当然如果有需要也可以使用Lua脚本
