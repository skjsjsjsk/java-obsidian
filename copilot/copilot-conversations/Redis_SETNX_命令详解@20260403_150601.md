### Redis 的 SETNX

- `SETNX` 的全称是 **SET if Not eXists**
- 含义是：**只有 key 不存在时，才会设置成功**
- 如果 key 已经存在，设置失败
- 返回值一般可以理解为：
  - `1`：设置成功
  - `0`：设置失败，说明 key 已存在

### 用它实现幂等的思路

- 客户端请求时携带一个**全局唯一的幂等号**，比如订单号、请求流水号
- 服务端先执行：
  - `SETNX idempotent:请求号 1`
- 如果返回 `1`，说明是第一次请求，可以继续执行业务
- 如果返回 `0`，说明这个请求已经处理过了，直接返回成功或提示重复提交

### 更推荐的写法

不要单独用 `SETNX`，而是直接用 Redis 的原子命令：

```bash
SET key value NX EX 60
```

比如：

```bash
SET idempotent:123456 1 NX EX 60
```

含义是：

- `NX`：只有 key 不存在时才设置
- `EX 60`：60 秒后自动过期

### 为什么要加过期时间

- 防止这个幂等标记一直存在，导致后续无法再次操作
- 避免服务异常后 key 永久残留
- 释放 Redis 内存

### 为什么不建议 `SETNX` 和 `EXPIRE` 分开写

比如这样：

```bash
SETNX idempotent:123456 1
EXPIRE idempotent:123456 60
```

有风险：

- 如果 `SETNX` 成功了
- 但在执行 `EXPIRE` 之前服务挂了
- 那么这个 key 就**没有过期时间**
- 会导致幂等标记长期存在，产生误判

所以面试里最好说：

- `SETNX` 可以实现幂等
- 但生产中更推荐使用 `SET key value NX EX timeout`，因为它把“判重”和“设置过期时间”做成了**原子操作**

### 适用场景

- 防止重复下单
- 防止表单重复提交
- 防止接口因为重试机制被重复消费
- 分布式环境下的简单幂等控制

### 要注意的问题

- Redis 幂等标记适合做**短时间防重**
- 如果是“必须永久保证不重复”，更稳妥的方案通常还是：
  - 数据库唯一约束
  - 去重表
- 因为 Redis 数据可能过期、丢失，不能完全替代数据库最终一致性的约束
