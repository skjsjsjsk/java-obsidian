## 一、先看是不是大表、业务是否允许短暂锁表

如果表很小、业务低峰、对抖动不敏感，可以直接执行：

```sql
ALTER TABLE xxx ADD COLUMN new_col VARCHAR(32) DEFAULT NULL;
```

但如果是线上核心大表，**不能直接无脑执行**，因为 `ALTER TABLE` 可能会导致：

- 持有元数据锁，阻塞读写
- 表重建，耗时很长
- 主从延迟
- 业务请求超时

所以线上加字段的核心就是：**尽量避免长时间锁表，降低对业务的影响。**

---

## 二、常见处理方案

### 1）优先看 MySQL 版本，能不能走 Online DDL

MySQL 5.6 之后支持部分 Online DDL，8.0 还支持一部分 `instant add column`。

比如：

```sql
ALTER TABLE xxx ADD COLUMN new_col INT NULL, ALGORITHM=INPLACE, LOCK=NONE;
```

或者在支持 instant 的场景下：

```sql
ALTER TABLE xxx ADD COLUMN new_col INT NULL, ALGORITHM=INSTANT;
```

这样做的好处是：

- 不需要重建整张表，或者代价更小
- 对线上业务影响较小
- 可以减少锁表时间

但是要注意：

- 不是所有加字段都能 `INSTANT`
- 如果字段位置不是最后、带复杂默认值、涉及行格式变化，可能退化成 `COPY`
- 即使是 Online DDL，也还是会拿 **MDL 锁**，只是通常时间较短

所以真正执行前，要先确认当前 MySQL 版本和这条 DDL 是否会退化。

---

### 2）大表更稳妥的方案：gh-ost / pt-online-schema-change

如果是大表、核心表，生产上更常见的是使用：

- `pt-online-schema-change`
- `gh-ost`

它们的核心思想其实差不多：

- 先创建一张新表，表结构是修改后的
- 在新表上加好字段
- 将旧表数据分批拷贝到新表
- 通过触发器或 binlog 同步增量变更
- 最后在一个很短的时间窗口内完成表切换

优点：

- 避免长时间锁表
- 对业务更平滑
- 适合千万级、上亿级大表

缺点：

- 操作复杂
- 需要额外磁盘空间
- 切换时仍有短暂风险，需要演练

如果面试官问“你们线上怎么做”，你可以答：

- 小表直接 DDL
- 大表优先评估 Online DDL
- 核心大表一般用 gh-ost 或 pt-osc 做无锁变更

---

## 三、加字段前要做哪些评估

这个很重要，面试官一般喜欢听“不是只会执行 SQL，而是知道风险控制”。

### 1）确认字段定义
要明确：

- 字段类型是否合适
- 是否允许为 `NULL`
- 默认值是什么
- 是否需要加注释
- 是否以后要建索引

一般建议：

- **先加可空字段或者默认值简单的字段**
- 不要一上来就加 `NOT NULL` 且回填大量数据，风险更大

---

### 2）评估是否会触发表重建
不同 MySQL 版本、不同 DDL 写法，代价不同。  
如果退化为 `COPY`，那风险很高。

---

### 3）关注主从复制
DDL 执行后可能出现：

- 从库执行慢
- 主从延迟增大
- 影响读流量

所以要：

- 观察复制延迟
- 在低峰期执行
- 必要时逐步切流

---

### 4）关注元数据锁 MDL
哪怕只是一个 DDL，如果有长事务一直占着表，`ALTER TABLE` 会被卡住；  
而一旦 DDL 在等 MDL，后续对这张表的新请求也可能被阻塞，最后把业务拖死。

所以执行前要先检查：

- 是否有长事务
- 是否有慢 SQL
- 是否有长时间未提交事务

这个点很关键，属于面试加分项。

---

## 四、实际更稳的做法：分步发布

线上加字段，通常不只是执行一条 DDL，而是**按兼容性分阶段发布**。

### 推荐流程：

### 第一步：先加字段，先不使用
比如：

```sql
ALTER TABLE user ADD COLUMN ext_info VARCHAR(255) NULL COMMENT '扩展信息';
```

此时代码还是老代码，不依赖这个字段。

---

### 第二步：应用发布新版本，兼容新旧字段
代码层面做到：

- 新字段为空时也能正常运行
- 新老版本代码都兼容
- 写入时可以开始补写新字段

---

### 第三步：异步回填历史数据
如果历史数据需要补齐，不要直接一条 SQL 全表更新：

```sql
UPDATE user SET ext_info = 'xxx';
```

因为这会：

- 产生大量行锁
- 产生大量 redo/undo/binlog
- 可能拖慢数据库

更好的方式是：

- 按主键范围分批更新
- 控制批次大小
- 每批提交一次
- 观察数据库负载

例如每次更新 1000 条、5000 条。

---

### 第四步：等数据回填完，再收紧约束
如果最终想改成 `NOT NULL`、加索引、加唯一约束，建议最后再做。

也就是：

- 先加字段
- 再回填
- 最后加约束/索引

这样风险最小。

---

## 五、如果面试官问“为什么不要直接加 NOT NULL 默认值”

你可以这样答：

因为这类 DDL 在某些 MySQL 版本下可能会导致：

- 表重建
- 长时间锁表
- 大量 IO
- 主从延迟

所以线上更常见的是：

- 先加 `NULL` 字段
- 应用兼容
- 分批回填
- 最后再改成 `NOT NULL`

这是一种典型的**灰度、兼容性变更思路**。

---

## 六、如果真的要答“线上操作步骤”

你可以整理成这个标准话术：

### 线上表加字段，我一般会这样做：

- 先评估表大小、MySQL 版本、业务是否允许抖动
- 检查这条 DDL 能否走 Online DDL 或 Instant DDL
- 执行前排查长事务，避免被 MDL 锁住
- 核心大表优先使用 gh-ost 或 pt-online-schema-change
- 选择业务低峰执行，并观察主从延迟、CPU、IO、连接数等指标
- 字段设计上优先加可空字段，避免一步到位加 `NOT NULL`
- 应用层先做兼容，再异步分批回填历史数据
- 数据回填完成后，再加约束或索引

---

## 七、面试精简版回答

如果你想背一个 1 分钟版本，可以直接说：

> 线上表加字段不能直接无脑执行 `ALTER TABLE`，尤其是大表，可能会导致表重建、元数据锁阻塞、主从延迟等问题。  
> 我一般会先评估 MySQL 版本和表大小，看能不能走 Online DDL 或 Instant Add Column。执行前会先排查长事务，避免 MDL 锁把业务卡住。  
> 如果是核心大表，通常会用 gh-ost 或 pt-online-schema-change 这类工具，先建新表、分批迁移数据、同步增量，最后再切表。  
> 在业务层面，我会采用兼容性发布，先加可空字段，不立即加 NOT NULL，等应用发布完成后再分批回填历史数据，最后再补约束和索引。这样对线上影响最小。
