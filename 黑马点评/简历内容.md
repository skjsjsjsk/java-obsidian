# 防止超卖和一人一单

- 最一开始通过查询数据库, 更新时带上`where 库存 > 0`防止超卖, 使用分布式锁保证一人一单
- 但是这个有大量请求访问数据库, 同时也会更新数据(会加锁), 同时还用分布式锁, 性能受到很大的影响

- 然后我就想到Redis是基于内存的, 读取速度非常块, 那么我完全可以把所有的操作放到Redis里完成, 但是为了保证原子性, 使用Lua脚本
- 使用Redis存储库存和订单信息和Lua脚本判断用户下单资格(防止超卖和一人一单), 保证不超买和一人一单
- 但是这个流程是同步的, 所以我做了优化

- 秒杀流程的最终优化: 
	- 我这个优化为, 核心使用 `使用Lua脚本进行资格校验, 异步使用消息队列去处理库存扣减和订单生成, 提高并发性能`
	- 因为扣减库存, 生产订单, 这些步骤都是对MySQL进行操作, 但是实际上对于秒杀来说, 当判断你有秒杀资格的那一步起, 你就秒杀成功了, 剩下的步骤就是为了实现秒杀, 所以完全可以异步来执行, 提高性能
	- 流程: 
		- **资格判断**: 当用户请求进来以后, 我会先做资格判断, 先查是否在秒杀券活动的时间内, 判断用户有无参与资格, 然后就执行Redis的Lua脚本, 原子的判断库存是否充足, 用户是否下过单, 通过的话, 就先在Redis里面预扣库存, 并把用户写入下单集合
		- **异步处理**: 拿到资格后, 我生成一个全局订单ID, 然后异步发送Kafka消息(`包含 orderId、userId 和 voucherId`), 让Kafka消费者去执行数据库和订单创建.   在消费者端, 我做了两层防护, 一层是先按userId加Redisson锁, 防止同一个用户并发消费, 另一层是在**事务里**再次校验**数据库是否已经下单**, 并且用`where 库存 > 0`的条件更新库存, 防止超卖, 扣库存成功, 才保存订单. 这样在数据库层还有一次兜底, 保证不超买, 不生产重复订单
		- **失败补偿**: 如果Kafka发送失败, 或者消费过程失败, 我会执行Redis回滚脚本, 把预占库存和用户资格释放掉
	- 追问: 
		- **面试官如果问“你这里的下单资格是什么”**: 
		- 你可以直接说：
		- 我这里的下单资格有三层含义：
			1. 活动时间上有资格，也就是当前时间在秒杀开始和结束时间之间
			2. 库存上有资格，也就是 Redis 里的秒杀库存还大于 0
			3. 用户维度上有资格，也就是这个用户还没有抢过这个券
		- 只有这三个条件都满足，我才允许发送 Kafka 下单消息。
