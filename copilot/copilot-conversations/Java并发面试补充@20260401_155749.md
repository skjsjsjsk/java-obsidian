# 一、建议补充的高频点

## 1. 一定要补：happens-before 原则
这是 **JMM 里面非常高频** 的点，你现在写了 JMM、volatile 的可见性和有序性，但如果面试官问：

- “JMM 怎么保证可见性？”
- “你知道 happens-before 吗？”
- “volatile 为什么能保证可见性？”

你现在这份笔记还缺一个总纲。

你可以补成：

- happens-before 是 JMM 中判断**操作之间内存可见性和有序性**的规则
- 如果操作 A happens-before 操作 B，那么 A 的执行结果对 B 可见，并且 A 排序在 B 之前
- 常见规则：
  - **程序次序规则**：同一个线程内，前面的操作 happens-before 后面的操作
  - **监视器锁规则**：对一个锁的解锁 happens-before 后面对这个锁的加锁
  - **volatile 变量规则**：对一个 volatile 变量的写 happens-before 后续对这个变量的读
  - **线程启动规则**：Thread 对象的 `start()` happens-before 线程中的操作
  - **线程终止规则**：线程中的所有操作 happens-before 其他线程检测到它终止（如 `join()` 返回）
  - **传递性**：如果 A happens-before B，B happens-before C，那么 A happens-before C

这个点一补，你的 JMM 体系会完整很多。

## 3. 建议补：wait / notify / notifyAll 的区别和使用条件
你写了 wait 和 sleep 的区别，但面试官还很喜欢继续问：

- “notify 和 notifyAll 有什么区别？”
- “为什么 wait/notify 必须在同步块里用？”

你可以补：

- `wait()` 会让当前线程进入等待队列，并且**释放锁**

## 1. volatile 和 synchronized 的区别
标准答法可以是：

- `volatile` 主要保证**可见性**和**有序性**，不能保证原子性
- `synchronized` 既能保证**原子性**，也能保证**可见性**和**有序性**
- `volatile` 适合一个线程写、多个线程读，或者状态标记这种场景
- `synchronized` 适合临界区复合操作

---

## 2. CAS 和 synchronized 区别
- CAS 是乐观锁思想，失败时重试，不阻塞线程
- synchronized 是悲观锁思想，竞争失败会阻塞挂起
- CAS 在低冲突场景性能好
- synchronized 在高冲突场景更稳定，避免大量自旋浪费 CPU
- CAS 会有 ABA 和自旋开销问题

---

## 3. ThreadLocal 为什么会内存泄漏
标准答法：

- `ThreadLocalMap` 的 key 是弱引用，value 是强引用
- 当 ThreadLocal 对象没有外部强引用时，key 会被 GC 回收
- 但 value 仍然被 Entry 强引用着
- 如果线程长期存活，尤其在线程池中，就可能导致 value 无法释放
- 解决办法是使用完后及时 `remove()`

# [[并发编程]]

## 1. 进程和线程的区别

- 进程是操作系统中 **资源分配的最小单位**
- 线程是操作系统中 **CPU 调度的最小单位**
- 一个进程中可以有多个线程，线程共享进程的资源，比如堆、方法区、文件句柄等
- 线程有自己独立的程序计数器、虚拟机栈、本地方法栈

### 面试回答
- 进程更像是一个运行中的程序实例，线程是进程中的执行单元
- 一个进程至少有一个线程
- 多线程的好处是可以提高程序并发能力，但因为线程共享资源，所以会带来线程安全问题

---

## 2. 线程的创建方式

### 2.1 继承 Thread 类
- 重写 `run()` 方法
- 调用 `start()` 启动线程

### 2.2 实现 Runnable 接口
- 实现 `run()` 方法
- 再把 Runnable 对象传给 Thread

### 2.3 实现 Callable 接口
- 实现 `call()` 方法
- 可以有返回值，还可以抛异常
- 一般结合 `FutureTask` 使用

```java
Callable<Integer> callable = () -> 1;
FutureTask<Integer> futureTask = new FutureTask<>(callable);
new Thread(futureTask).start();
Integer result = futureTask.get();
```

### 面试回答
- 常见有 3 种：继承 Thread、实现 Runnable、实现 Callable
- 实际开发中更推荐实现 Runnable 或 Callable，因为这样可以避免单继承局限，也更符合任务和线程分离的思想

---

## 3. 调用 start() 和直接调用 run() 的区别

- 直接调用 `run()`，本质上只是普通方法调用，**不会创建新线程**
- 调用 `start()` 才会通知 JVM 创建新的线程，线程创建成功后会由该新线程执行 `run()` 方法

### 面试回答
- `run()` 是普通方法，`start()` 才是真正启动线程的方法
- 所以想实现并发，必须调用 `start()`，不能直接调用 `run()`

---

## 4. 线程的状态

Java 中线程有 6 种状态：

- `NEW`：新建状态，线程对象已经创建，但还没有调用 `start()`
- `RUNNABLE`：可运行状态，**包含就绪和运行中**
- `BLOCKED`：阻塞状态，等待获取监视器锁
- `WAITING`：无限期等待状态
- `TIMED_WAITING`：超时等待状态
- `TERMINATED`：终止状态，线程执行完毕

### 常见场景
- 调用 `sleep()` 后进入 `TIMED_WAITING`
- 调用无参 `wait()` 后进入 `WAITING`
- 调用有超时参数的 `wait()` 后进入 `TIMED_WAITING`
- 等待进入 synchronized 代码块但拿不到锁时进入 `BLOCKED`

---

## 5. sleep 和 wait 的区别

### 相同点
- 都可以让当前线程暂停执行

### 不同点
- `sleep()` 是 `Thread` 类的方法，`wait()` 是 `Object` 类的方法
- `sleep()` **不会释放锁**，`wait()` **会释放锁**
- `sleep()` 可以在任何地方调用，`wait()` 必须在同步代码块或同步方法中调用
- `sleep()` 到时间会自动恢复，`wait()` 需要 `notify()` 或 `notifyAll()` 唤醒，或者等待超时

### 面试回答
- 最大区别是：`sleep()` 不释放锁，`wait()` 会释放锁
- 所以 `wait/notify` 常用于线程通信，而 `sleep` 更像是线程主动休眠

---

## 6. notify 和 notifyAll 的区别

- `notify()`：随机唤醒一个等待该对象监视器锁的线程
- `notifyAll()`：唤醒所有等待该对象监视器锁的线程，最终谁抢到锁谁继续执行

### 为什么 wait/notify 必须在 synchronized 中使用
- 因为它们操作的是对象监视器
- 调用这些方法时，当前线程必须持有该对象的监视器锁
- 否则会抛出 `IllegalMonitorStateException`

---

## 7. join、yield、interrupt

## 7.1 join
- `join()` 的作用是让当前线程等待目标线程执行完毕

### 例子
- 主线程等待子线程执行完，再汇总结果

## 7.2 yield
- `yield()` 表示当前线程愿意让出 CPU
- 只是对调度器的提示，不一定生效

## 7.3 interrupt
- `interrupt()` 不是强制终止线程，而是设置线程的中断标记
- 如果线程正处于 `sleep()`、`wait()`、`join()` 等阻塞状态，会抛出 `InterruptedException`
- 如果线程处于运行状态，只是把中断标记设为 `true`，需要线程自己决定是否退出

### 两个方法
- `isInterrupted()`：获取中断标记，**不清除**
- `Thread.interrupted()`：获取当前线程中断标记，**并清除**

### 面试回答
- interrupt 本质上是一种协作式中断，不是暴力停止线程

---

## 8. 线程安全问题是怎么产生的

线程安全问题出现的根本原因有两个：

- **共享资源**
- **多个线程并发操作**

比如 `i++` 不是线程安全的，因为它不是原子操作，大致分为三步：

- 读取 i
- i + 1
- 把结果写回

多个线程同时执行时，就可能出现结果错误

---

## 9. Java 内存模型 JMM

JMM 规定了多线程环境下：

- 共享变量存储在哪里
- 线程之间如何通信
- 指令能否重排序
- 如何保证可见性、有序性、原子性

### 主内存和工作内存
- 共享变量存储在主内存中
- 每个线程都有自己的工作内存
- 线程对变量的读写，通常先在工作内存中进行，再同步回主内存

### JMM 主要解决的问题
- **可见性**：一个线程修改的变量，另一个线程能否马上看到
- **有序性**：程序执行顺序是否符合预期
- **原子性**：操作是否不可分割

---

## 10. happens-before 原则

happens-before 是 JMM 中判断 **可见性和有序性** 的核心规则。

如果操作 A happens-before 操作 B，那么：
- A 的执行结果对 B 可见
- A 排序在 B 之前

### 常见规则
- **程序次序规则**：同一个线程内，前面的操作 happens-before 后面的操作
- **监视器锁规则**：对一个锁的解锁 happens-before 后面对这个锁的加锁
- **volatile 变量规则**：对一个 volatile 变量的写 happens-before 后续对该变量的读
- **线程启动规则**：`start()` happens-before 线程中的操作
- **线程终止规则**：线程中的所有操作 happens-before 其他线程检测到该线程终止
- **传递性**：如果 A happens-before B，B happens-before C，那么 A happens-before C

### 面试回答
- happens-before 是 JMM 里判断多线程操作之间是否可见、是否有序的重要规则

---

## 11. volatile 关键字

`volatile` 可以保证：

- **可见性**
- **有序性**

但 **不能保证原子性**

### 11.1 可见性
- 一个线程修改了 volatile 变量，会立即刷新到主内存
- 其他线程读取 volatile 变量时，会从主内存读取最新值

### 11.2 有序性
- volatile 会通过内存屏障禁止特定的指令重排序

### 11.3 不保证原子性
比如：

```java
volatile int count = 0;
count++;
```

`count++` 仍然不是原子操作，所以线程不安全

### 使用场景
- 状态标记位
- 一个线程写，多个线程读
- 双重检查单例中的实例引用

### 面试回答
- volatile 保证可见性和有序性，但不保证复合操作的原子性

---

## 12. synchronized 关键字

`synchronized` 可以保证：

- **原子性**
- **可见性**
- **有序性**

### 12.1 使用方式
- 修饰实例方法：锁的是当前对象 `this`
- 修饰静态方法：锁的是当前类的 `Class` 对象
- 修饰代码块：锁的是括号里的对象

### 12.2 底层原理
`synchronized` 底层依赖 JVM 的 **Monitor 监视器锁**

- 同步代码块通过字节码指令 `monitorenter` 和 `monitorexit` 实现
- 同步方法通过方法标志位 `ACC_SYNCHRONIZED` 实现

### 12.3 锁升级
经典 HotSpot 中，锁大致会经历：

- 无锁
- 偏向锁
- 轻量级锁
- 重量级锁

不过要注意：
- 偏向锁在较新的 JDK 版本中已经逐步废弃/移除
- 面试时可以说这是经典实现中的优化过程

### 面试回答
- synchronized 本质是基于 Monitor 实现的
- 它既能保证互斥访问，也能通过锁释放和加锁建立 happens-before 关系，从而保证可见性

---

## 13. volatile 和 synchronized 的区别

### volatile
- 保证可见性
- 保证有序性
- 不保证原子性
- 不会阻塞线程

### synchronized
- 保证原子性
- 保证可见性
- 保证有序性
- 线程竞争时会发生阻塞

### 面试回答
- volatile 适合做状态标记
- synchronized 适合保护临界区中的复合操作

---

## 14. Lock 和 ReentrantLock

`ReentrantLock` 是 JUC 中常用的显式锁。

### 特点
- 可重入
- 支持公平锁和非公平锁
- 支持可中断获取锁
- 支持超时获取锁
- 支持多个条件变量 `Condition`

### 常用方法
- `lock()`：加锁
- `unlock()`：解锁
- `tryLock()`：尝试获取锁
- `lockInterruptibly()`：可中断获取锁

### 和 synchronized 的区别
- `synchronized` 是 JVM 层面实现，使用简单，自动释放锁
- `ReentrantLock` 是 API 层面实现，功能更丰富，但必须手动释放锁

### 面试回答
- 两者都可重入
- ReentrantLock 功能更强，适合复杂同步场景
- synchronized 写法更简单，JDK 1.6 之后性能也优化得很好

---

## 15. 公平锁和非公平锁

- **公平锁**：按照线程等待顺序获取锁
- **非公平锁**：允许线程插队获取锁

### 区别
- 公平锁更公平，但吞吐量通常较低
- 非公平锁吞吐量更高，所以默认一般是非公平锁

---

## 16. 乐观锁和悲观锁

### 悲观锁
- 认为并发冲突一定会发生
- 每次访问共享资源都先加锁
- 典型实现：`synchronized`、`ReentrantLock`

### 乐观锁
- 认为并发冲突不一定发生
- 更新数据时先尝试，不行就重试
- 典型实现：CAS

---

## 17. CAS

CAS 全称 Compare And Swap，比较并交换。

包含 3 个值：

- V：内存中的实际值
- A：预期值
- B：要更新的新值

如果 `V == A`，就把 V 更新成 B；
如果不相等，说明有其他线程修改过，更新失败

### 优点
- 不加锁，性能高
- 适合低冲突场景

### 缺点
- 会有 ABA 问题
- 高并发下会不断自旋，浪费 CPU
- 只能保证单个变量操作的原子性

### ABA 问题
- 一个值从 A 变成 B，又变回 A
- CAS 会误认为这个值没有变过

### ABA 的解决
- 可以使用版本号
- 例如 `AtomicStampedReference`

---

## 18. 原子类

JUC 提供了一系列原子类，底层一般基于 CAS + volatile 实现。

### 常见原子类
- `AtomicInteger`
- `AtomicLong`
- `AtomicBoolean`
- `AtomicReference`

### LongAdder
- 在高并发计数场景下，性能通常优于 `AtomicLong`
- 核心思想是把热点拆分到多个槽中，最后再汇总，减少 CAS 冲突

### 面试回答
- AtomicInteger 适合一般并发计数
- LongAdder 更适合高并发统计场景

---

## 19. AQS

AQS 全称 `AbstractQueuedSynchronizer`，是很多并发工具的基础框架。

### 核心思想
- 用一个 `volatile int state` 表示同步状态
- 用一个 FIFO 双向队列维护获取锁失败的线程

### 两种模式
- **独占模式**：如 `ReentrantLock`
- **共享模式**：如 `CountDownLatch`、`Semaphore`、读写锁的读锁

### 基于 AQS 的常见类
- `ReentrantLock`
- `CountDownLatch`
- `Semaphore`
- `ReentrantReadWriteLock`

## 20. LockSupport

`LockSupport` 用来阻塞和唤醒线程。

### 方法
- `park()`：阻塞当前线程
- `unpark(thread)`：唤醒指定线程

### 作用
- AQS 底层很多线程挂起和唤醒操作都依赖它实现

## 21. ThreadLocal

### 21.1 是什么
`ThreadLocal` 用于创建线程局部变量，为每个线程提供独立副本，实现线程隔离

### 21.2 实现原理
不是 ThreadLocal 内部维护 Map，而是：

- 每个 `Thread` 对象内部有一个 `ThreadLocalMap`
- `ThreadLocalMap` 的 key 是 `ThreadLocal` 对象
- value 是线程存储的数据

### 21.3 使用过程
调用 `get()` 时：
- 先拿到当前线程 `Thread.currentThread()`
- 再拿到线程内部的 `ThreadLocalMap`
- 最后根据当前 ThreadLocal 作为 key 查找对应 value

### 21.4 作用
- 实现线程隔离
- 避免共享变量竞争
- 常见于保存用户信息、数据库连接、事务上下文等

### 21.5 内存泄漏问题
- `ThreadLocalMap` 的 key 是弱引用
- value 是强引用
- 当 ThreadLocal 对象没有外部强引用时，key 可能被回收
- 但 value 还在，可能无法及时释放
- 在线程池场景下，因为线程会复用，问题更明显

### 解决办法
- 使用完及时调用 `remove()`

### 面试回答
- ThreadLocal 不是解决共享问题，而是通过线程隔离避免线程安全问题

---

## 22. 线程池

### 22.1 为什么要用线程池
- 降低线程创建和销毁开销
- 提高响应速度
- 提高线程复用率
- 便于统一管理线程

### 22.2 ThreadPoolExecutor 核心参数

- `corePoolSize`：核心线程数
- `maximumPoolSize`：最大线程数
- `keepAliveTime`：非核心线程空闲存活时间
- `unit`：时间单位
- `workQueue`：任务队列
- `threadFactory`：线程工厂
- `handler`：拒绝策略

### 22.3 执行流程
当新任务提交到线程池时：

- 如果当前线程数小于 `corePoolSize`，创建核心线程执行任务
- 否则尝试把任务放入阻塞队列
- 如果队列已满，且当前线程数小于 `maximumPoolSize`，创建非核心线程执行任务
- 如果队列已满且线程数已经等于 `maximumPoolSize`，执行拒绝策略

### 22.4 常见阻塞队列
- `ArrayBlockingQueue`：有界数组队列
- `LinkedBlockingQueue`：链表队列，可有界也可无界
- `SynchronousQueue`：不存储元素，生产一个必须消费一个
- `PriorityBlockingQueue`：优先级队列

### 22.5 常见拒绝策略
- `AbortPolicy`：直接抛异常
- `CallerRunsPolicy`：由调用线程执行任务
- `DiscardPolicy`：直接丢弃任务
- `DiscardOldestPolicy`：丢弃队列中最老的任务

### 22.6 shutdown 和 shutdownNow
- `shutdown()`：不再接收新任务，但会继续执行已提交的任务
- `shutdownNow()`：尝试中断正在执行的任务，并返回队列中未执行的任务

---

## 23. 为什么不推荐直接使用 Executors 创建线程池

### 原因
- `newFixedThreadPool()` 和 `newSingleThreadExecutor()` 使用的是 **无界队列**
- 如果任务堆积过多，可能导致 OOM
- `newCachedThreadPool()` 的线程数上限非常大，可能创建大量线程，也可能导致 OOM

### 正确做法
- 生产环境一般手动创建 `ThreadPoolExecutor`
- 明确指定核心线程数、最大线程数、队列大小和拒绝策略

### 面试回答
- 不推荐 Executors 的核心原因是资源边界不清晰，容易导致内存问题或线程数失控

---

## 24. 线程池参数如何设置

这个问题面试也很常见。

### CPU 密集型任务
- 线程数一般设置为 CPU 核心数 + 1

### IO 密集型任务
- 线程数一般可以设置得比 CPU 核心数大一些
- 常见经验值：$2 \times CPU核数$

### 实际上
- 需要结合任务类型、机器配置、响应时间要求、队列容量等综合考虑

---

## 25. 线程池里 submit 和 execute 的区别

### execute
- 没有返回值
- 适用于不需要返回结果的任务

### submit
- 有返回值，返回 `Future`
- 可以获取执行结果，也可以捕获异常

### 区别总结
- `execute()` 更简单
- `submit()` 更适合需要结果或异常处理的场景

## 26. ConcurrentHashMap

### 26.1 为什么 HashMap 线程不安全
在多线程环境下，HashMap 可能出现：

- 数据覆盖
- 丢失更新
- 扩容时链表形成环，导致死循环（JDK7 头插法下更明显）

### 26.2 ConcurrentHashMap 的实现

#### JDK7
- 采用 **Segment 分段锁**
- 每个 Segment 类似一个小 HashMap，锁粒度比整个表小

#### JDK8
- 采用 **数组 + 链表 + 红黑树**
- 通过 **CAS + synchronized + volatile** 保证线程安全

### 26.3 JDK8 中 put 大致流程
- 如果桶为空，先尝试 CAS 插入
- 如果冲突，再对桶头节点加 synchronized 锁
- 链表过长时可能转红黑树

### 26.4 树化条件
- 当链表长度达到 8，且数组长度大于等于 64 时，才会树化
- 如果数组长度较小，会优先扩容而不是树化

### 26.5 读操作
- 大多数 `get()` 场景下不需要加锁
- 主要依赖 volatile 保证可见性

### 面试回答
- JDK8 的 ConcurrentHashMap 主要通过 CAS + synchronized + volatile 实现线程安全
- 相比 Hashtable，锁粒度更细，并发性能更高

---

## 27. CopyOnWriteArrayList

### 原理
- 写操作时先复制一份底层数组
- 在新数组上修改
- 修改完成后再把引用指向新数组

### 优点
- 读操作不加锁，性能高
- 适合读多写少场景

### 缺点
- 写操作开销大
- 内存占用高
- 数据一致性是弱实时的

---

## 28. 读写锁

## 28.1 ReentrantReadWriteLock
特点：

- 读读共享
- 读写互斥
- 写写互斥

适用场景：
- 读多写少

### 面试回答
- 读写锁通过区分读操作和写操作，提高了读多写少场景下的并发性能

## 29. 常见并发工具类

## 29.1 CountDownLatch
- 一个线程等待其他线程完成后再继续执行
- 内部维护一个计数器
- 计数器减到 0 后，等待线程被唤醒
- 一次性使用，不能重置

## 29.2 CyclicBarrier
- 让一组线程互相等待，到达屏障点后再一起继续执行
- 可以重复使用

## 29.3 Semaphore
- 信号量，用来限制同时访问某个资源的线程数量
- 常用于限流、连接池控制

### 面试回答
- CountDownLatch 强调“等别人”
- CyclicBarrier 强调“大家互相等”
- Semaphore 强调“限流”

---

## 30. 死锁

### 什么是死锁
多个线程互相持有对方需要的资源，并且都不释放，导致线程永远等待

### 死锁产生的 4 个必要条件
- 互斥
- 请求并保持
- 不可剥夺
- 循环等待

### 如何避免死锁
- 固定加锁顺序
- 一次性申请所有资源
- 使用超时锁 `tryLock()`
- 减少锁的嵌套

---

## 31. synchronized 和 ReentrantLock 的选择

### synchronized 适合
- 代码简单
- 锁逻辑不复杂
- 自动释放锁，使用更安全

### ReentrantLock 适合
- 需要可中断锁
- 需要超时获取锁
- 需要公平锁
- 需要多个条件变量

## 32. 面试高频问题总结

## 32.1 volatile 和 synchronized 的区别
- volatile 保证可见性和有序性，不保证原子性
- synchronized 保证原子性、可见性和有序性

## 32.2 CAS 和 synchronized 的区别
- CAS 是乐观锁，不阻塞线程
- synchronized 是悲观锁，竞争失败会阻塞
- CAS 适合低冲突场景
- synchronized 在高冲突场景更稳定

## 32.3 ThreadLocal 为什么会内存泄漏
- key 是弱引用，value 是强引用
- key 被回收后，value 可能还在
- 线程池中更容易出现
- 使用完及时 `remove()`

## 32.4 ConcurrentHashMap 为什么线程安全
- JDK7：分段锁
- JDK8：CAS + synchronized + volatile

## 32.5 为什么不推荐 Executors
- 可能导致无界队列堆积或线程数失控，最终 OOM

## 33. 一些常见面试题标准话术

### 33.1 说一下 volatile
- volatile 可以保证变量的可见性和有序性，但不能保证复合操作的原子性
- 它比较适合状态标记位，或者一个线程写多个线程读的场景

### 33.2 说一下 synchronized
- synchronized 底层依赖 Monitor 实现
- 同步代码块通过 monitorenter 和 monitorexit 实现
- 它既可以保证互斥访问，也能保证可见性和有序性

### 33.3 说一下 CAS
- CAS 是一种无锁的原子更新机制，核心是比较内存值和预期值是否一致，一致才更新
- 它性能高，但会有 ABA 和自旋开销问题

### 33.4 说一下 ThreadLocal
- ThreadLocal 的核心作用是线程隔离
- 每个线程内部都有自己的 ThreadLocalMap
- 不同线程访问的是自己的副本，所以不会互相影响

### 33.5 说一下线程池执行流程
- 核心线程先执行
- 核心线程满了后进入队列
- 队列满了再创建非核心线程
- 都满了就执行拒绝策略
