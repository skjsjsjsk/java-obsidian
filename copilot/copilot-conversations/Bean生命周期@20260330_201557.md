## Bean 的生命周期

Spring 中 Bean 的生命周期，大致可以分为 **实例化、属性注入、初始化、使用、销毁** 这几个阶段。

### 1. 实例化
Spring 容器首先会通过构造方法或者工厂方法来创建 Bean 对象，此时对象已经存在，但是里面的属性还没有赋值。

### 2. 属性注入
Spring 会对 Bean 进行依赖注入，也就是给对象中的成员变量赋值，比如通过 `@Autowired`、`@Resource` 注入其他 Bean。

### 3. 初始化
初始化阶段是面试中最容易问细节的地方，一般可以按顺序说：

- 回调 Aware 接口
- 执行 BeanPostProcessor 前置处理
- 执行初始化方法
- 执行 BeanPostProcessor 后置处理

其中：

#### 3.1 回调 Aware 接口
Aware 接口主要分为两类：

- BeanFactory 级别
  - `BeanNameAware`
  - `BeanClassLoaderAware`
  - `BeanFactoryAware`

- ApplicationContext 级别
  - `ApplicationContextAware`
  - `EnvironmentAware`
  - `ResourceLoaderAware`
  - `ApplicationEventPublisherAware`
  - `MessageSourceAware`

它的作用是让 Bean 感知 Spring 容器提供的一些基础信息和能力。

#### 3.2 BeanPostProcessor 前置处理
会执行 Bean 后置处理器中的前置方法，也就是：

- `postProcessBeforeInitialization()`

#### 3.3 执行初始化方法
初始化方法的执行顺序一般是：

- `@PostConstruct`
- `InitializingBean` 的 `afterPropertiesSet()`
- 自定义的 `init-method`

#### 3.4 BeanPostProcessor 后置处理
最后执行：

- `postProcessAfterInitialization()`

Spring AOP 的代理对象，通常就是在这个阶段创建出来的。

### 4. 使用 Bean
初始化完成后，Bean 就可以被业务代码正常使用了，比如 Controller 调用 Service，Service 调用 DAO。

### 5. 销毁
当容器关闭时，Spring 会销毁 Bean，执行顺序一般是：

- `@PreDestroy`
- `DisposableBean` 的 `destroy()`
- 自定义的 `destroy-method`

# Bean 生命周期面试追问版

## 1. Bean 生命周期和循环依赖有什么关系？

Bean 生命周期和循环依赖的关系主要在 **实例化、属性注入、初始化** 这几个阶段。

因为循环依赖通常发生在 **属性注入阶段**：

- Spring 先实例化 Bean A
- A 还没初始化完成，就要注入 Bean B
- Spring 又去创建 Bean B
- B 在注入时又依赖 A
- 这时候如果 A 完全没法提前暴露出来，就会发生循环依赖无法解决

所以 Spring 为了解决这个问题，会在 Bean **实例化之后、初始化之前**，把一个“早期对象”提前暴露出去，这样别的 Bean 在依赖它时，就能先拿到引用。

也就是说：

- 循环依赖的本质是：两个或多个 Bean 在创建过程中互相引用
- Spring 能解决的前提是：**单例 Bean + 属性注入**
- 解决的关键是：**提前暴露对象**

---

## 2. Spring 怎么解决循环依赖？

Spring 主要通过 **三级缓存** 来解决单例 Bean 的属性注入循环依赖。

### 三级缓存分别是什么

- 一级缓存 `singletonObjects`
  - 存放已经完全初始化好的单例 Bean

- 二级缓存 `earlySingletonObjects`
  - 存放提前暴露的早期 Bean 对象

- 三级缓存 `singletonFactories`
  - 存放 Bean 的对象工厂，用来在需要时生成早期对象，必要时还能生成早期代理对象

---

## 3. 循环依赖的解决流程

假设 A 依赖 B，B 又依赖 A：

### 第一步：创建 A
- Spring 先实例化 A
- 这时候 A 只是一个空对象，属性还没注入
- Spring 把 A 对应的对象工厂放入三级缓存

### 第二步：A 注入 B
- 发现 B 还没创建，于是去创建 B

### 第三步：创建 B
- Spring 实例化 B
- 同样先把 B 的对象工厂放入三级缓存
- 然后给 B 注入属性，发现 B 依赖 A

### 第四步：B 需要 A
- Spring 去获取 A
- 一级缓存没有
- 二级缓存没有
- 三级缓存有 A 的对象工厂
- 通过对象工厂拿到 A 的早期引用
- 并把这个早期引用放入二级缓存

### 第五步：B 完成初始化
- B 成功拿到 A 的引用后，就可以完成属性注入和初始化
- 初始化完成后，B 放入一级缓存

### 第六步：A 再继续创建
- A 现在可以顺利注入 B
- 然后完成自己的初始化
- 最后 A 也放入一级缓存

这样 A 和 B 就都创建成功了。

---

## 4. 为什么是三级缓存，不是二级缓存？

这个问题很高频。

核心原因是：**为了解决 AOP 代理的问题**。

如果只有二级缓存，那么在 Bean 还没初始化的时候，就得提前决定往缓存里放：

- 原始对象
- 还是代理对象

这时候其实还不一定能确定，因为 AOP 代理通常是在初始化后才创建的。

所以 Spring 多设计了一层三级缓存：

- 三级缓存里放的不是对象本身，而是 `ObjectFactory`
- 当别的 Bean 需要这个早期对象时，再通过工厂方法决定返回：
  - 原始对象
  - 或者早期代理对象

这样更灵活，也避免了同一个 Bean 在容器里出现两个不同对象的问题。

---

## 5. AOP 代理为什么会影响循环依赖？

因为 Spring 在解决循环依赖时，提前暴露出去的对象，可能不是原始对象，而是 **代理对象**。

举个例子：

- A 这个 Bean 后面要被 Spring AOP 增强
- 那么 B 在依赖 A 时，最好拿到的就是 A 的代理对象
- 这样 B 调用 A 的方法时，事务、日志、权限等切面逻辑才能生效

如果 B 拿到的是 A 的原始对象，而最后容器里放进去的是 A 的代理对象，那么就会出现：

- 容器中的 A 是代理对象
- B 持有的却是原始对象

这样就不一致了，AOP 也可能失效。

所以 Spring 才会在三级缓存里通过对象工厂，必要时提前暴露一个 **早期代理对象**。

---

## 6. AOP 代理对象是在 Bean 生命周期的哪个阶段创建的？

一般来说，AOP 代理对象是在 **初始化后阶段** 创建的，也就是：

- `BeanPostProcessor#postProcessAfterInitialization()`

最典型的就是 `AbstractAutoProxyCreator` 这类后置处理器，会在这个阶段判断当前 Bean 是否需要增强，如果需要，就返回代理对象。

所以正常情况下：

- 前面实例化出来的是原始对象
- 到初始化后，Spring 才可能把它包装成代理对象

这也是为什么循环依赖必须考虑“提前代理”的问题。

---

## 7. 哪些循环依赖 Spring 解决不了？

Spring 不是所有循环依赖都能解决，它只能解决一部分。

### 能解决的
- 单例 Bean
- 通过属性注入产生的循环依赖

比如：

- A 中 `@Autowired` B
- B 中 `@Autowired` A

这种一般可以解决。

### 不能解决的

#### 1. 构造器循环依赖
比如：

```java
public class A {
    public A(B b) {}
}

public class B {
    public B(A a) {}
}
```

这种不行，因为：

- 构造器注入时，对象连实例化都还没完成
- 根本没办法提前暴露引用

#### 2. Prototype Bean 循环依赖
多例 Bean 也解决不了，因为 Spring 不会缓存 prototype Bean，自然也没有三级缓存这一套机制。

#### 3. 某些复杂的 AOP 代理场景
如果提前暴露的对象和最终对象不一致，或者出现多层代理、异常代理链等复杂情况，也可能导致循环依赖失败。

---

## 8. `@PostConstruct` 和构造方法有什么区别？

这个也很常考。

### 构造方法
- 在对象实例化时执行
- 这时候对象刚被创建出来
- 依赖注入通常还没完成
- 所以不适合使用还未注入的成员变量

### `@PostConstruct`
- 在依赖注入完成之后执行
- 属于初始化阶段
- 这时候 Bean 的属性基本已经准备好了
- 更适合做一些初始化逻辑

### 一句话总结
- 构造方法：负责“对象出生”
- `@PostConstruct`：负责“对象准备完成后的初始化”

---

## 9. `@PostConstruct`、`afterPropertiesSet()`、`init-method` 的执行顺序是什么？

执行顺序是：

- `@PostConstruct`
- `InitializingBean#afterPropertiesSet()`
- 自定义 `init-method`

面试时可以补一句：

- 这三种都是初始化方法
- 只是触发方式不同
- 一般更推荐 `@PostConstruct`，侵入性更低

---

## 10. BeanPostProcessor 有什么作用？

`BeanPostProcessor` 是 Spring 非常重要的扩展点。

它可以在 Bean 初始化前后进行处理：

- `postProcessBeforeInitialization()`
- `postProcessAfterInitialization()`

常见用途：

- AOP 生成代理对象
- 对 Bean 进行统一增强
- 实现一些框架级扩展功能

可以理解为：

- Bean 生命周期中的“拦截器”
- Spring 很多高级功能都建立在它之上

---

## 11. 为什么说 Spring 解决循环依赖依赖于“提前暴露”？

因为如果等到 Bean 完全初始化结束后再放入容器，那在依赖注入过程中，其他 Bean 根本拿不到它。

所以 Spring 的做法是：

- Bean 刚实例化完成
- 虽然还没初始化
- 但先把一个早期引用暴露出去
- 让别的 Bean 可以先注入它
- 然后等整个创建流程结束，再把完整对象放入一级缓存

这就是循环依赖能被解决的关键。

# 面试完整回答模板

如果面试官连续问，你可以这样答：

- Spring Bean 生命周期主要包括实例化、属性注入、初始化、使用和销毁。
- 初始化阶段会先回调 Aware 接口，然后执行 `BeanPostProcessor` 前置方法，再执行 `@PostConstruct`、`afterPropertiesSet()`、`init-method`，最后执行后置方法，这一步通常会创建 AOP 代理对象。
- Spring 解决循环依赖，主要是依赖三级缓存。因为循环依赖通常发生在属性注入阶段，所以 Spring 会在 Bean 实例化之后、初始化之前提前暴露一个早期对象。
- 一级缓存存完整 Bean，二级缓存存早期对象，三级缓存存对象工厂。三级缓存的意义主要是为了解决 AOP 代理问题，必要时可以提前暴露代理对象，而不是原始对象。
- 但是 Spring 只能解决单例 Bean 的属性注入循环依赖，像构造器循环依赖和 prototype Bean 循环依赖是解决不了的。
