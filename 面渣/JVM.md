- JVM组成结构: 包括四大核心组件和运行时数据区
	- 核心组件: 
		- 类加载子系统: 把 `.class` 文件加载到内存中生成 `Class` 对象
		- 执行引擎: 解释或编译字节码为机器码的
		- 本地库接口: 让Java支持本地代码, 通过JNI实现
		- 垃圾回收器: 自动管理内存, 回收堆中不用的对象
	- JVM内存结构(运行时数据区): 首先不要与JMM(Java内存模型)搞混
		- JVM内存结构大体上分为两类, 分别是线程私有区域和线程共享区域, 线程私有区域里包括了程序计数器, 虚拟机栈和本地方法栈, 线程共享区域里有堆和方法区
		- 程序计数器: 它又被叫做PC寄存器, 记录当前线程执行的字节码指令的地址, 唯一不会发生OOM的区域
		- 虚拟机栈: 它的生命周期与线程相同, 每个方法在执行的时候都会创建一个栈帧, 用来存储局部变量表, 动态链接等等, 栈帧会被压到虚拟机栈中, 当方法执行结束的时候, 栈帧会被移除
		- 本地方法栈: 当Java执行Native方法时会使用它, 与虚拟机栈相似
		- 堆: 堆是JVM中最大的一块, 也是进行垃圾回收的主要区域, 为了维持垃圾回收, 堆被分为了新生代与老年代, 新生代又被分为了Eden区和Survivor区, Survivor区里面分为了From和To区
		- 方法区: 并不存在, 只是Java虚拟机中的一个概念, 用来存储静态变量, 常量等等
			- 延申问道, 堆与栈的区别: 
				- 堆是线程共享的, Java中几乎所有new出来的对象都会在堆上进行分配, 它的生命周期不受单个方法所影响, 只有当不被任何变量引用的时候, 才会被垃圾收集器回收
				- 而栈是私有的, 主要用来存储池局部变量, 对象引用等等, 它随着方法调用的结束而结束, 不需要使用垃圾收集器, 会自动释放
		- 在JDK1.7以前, 方法区叫做永久代, 和堆连到一起; JDK1.8以后, 废弃了永久代, 引入了元空间, 把它从JVM内存移动到了本地内存中
- 对象创建和销毁的过程: 
	- 创建: 
		- 当你new一个新对象的时候, JVM首先会在常量池里查找有没有该类的符号引用, 然后看该符号引用代表的类是否已经被加载, 解析和初始化了, 如果没有, 就进行类加载.      
		- 类被加载完毕后, JVM就会给该对象分配内存
		- 然后进行初始化(设置默认值).  这一步是为了保证对象的实例字段在 Java 代码中可以不赋初始值就直接使⽤
		- 接下来设置对象头, 对象头里面有该对象的类实例, GC的分代情况等等, 
		- 最后执行`<init>`构造方法完成赋值操作, 把成员变量赋值成预期的值
	- 销毁: 首先垃圾回收器会通过可达性算法判断对象是否还被引用, 如果引用则存活, 否则视为垃圾, 然后就使用 标记-清除, 复制 和 标记-整理 等算法进行垃圾回收, 释放该对象所占用的内存空间
- 什么情况对象会进入老年代(四种):  
	- 大对象: 如果该对象是一个大对象, (就是大于一个阈值(只对 Serial/ParNew 有效), 这个可以由自己定, 大于这个时它就被判定为一个大对象)(还有就是如果是G1垃圾收集器时, 堆里面有专门给大对象分配的空间, 当大对象大于区域内存的一半的时候, 就认为是大对象, 被分配到大对象区), 大对象会直接进入老年代
	- 15次GC: 在年轻代里面存活时间过长, 当一个对象经历过15次Minor GC依旧存活的时候, 那么下一次它就会进入老年代
	- 动态年龄: 程序从年龄最小的对象开始累加，如果累加的对象大小所占用的内存大于Survivor区内存的一半以上的时候, >=该年龄的对象会直接进入老年代
	- Minor GC 后 Survivor 放不下，部分存活对象会通过空间分配担保进入老年代
	- 空间分配担保机制: 
		1. 就是会在Minor GC前进行检查, 如果当前老年代中最大可用连续内存空间大于年轻代所有对象的总空间, 那么是该次GC是安全的, 会发起GC.                         
		2. 如果小于, 那么就会看是否设置了HandlePromotionFailure这个参数, 如果没有, 那么就执行full GC
		3. 如果有, 那么就会看老年代的最大连续内存空间是否大于历次晋升到老年代对象的平均大小, 如果小于就full GC
		4. 否则, 就进行Minor GC, 该次GC后, 会检查Survivor的空间是否能够放下存活对象, 如果不可以, 就放入老年代, 否则就放到Survivor空间中.  如果老年代都放不下所有的存活对象, 那么就担保失败, 进行full GC
- JVM的垃圾回收: 
	- 垃圾回收就是对堆内存里面那些已经死亡或者长时间不被引用的对象进行回收, 释放占用的内存, 这就是垃圾回收
	- GC知道吗, 如何判断垃圾的, 如何判断对象是否可以被回收: JVM在GC之前, 会通过可达性算法, 从**GC Roots**出发(像虚拟机栈中的引用了(比如局部变量或者方法参数), 本地方法栈中的JNI引用了, 类静态变量引用了或者运行时常量池的常量等等), 标记可以到达的对象, 未被标记的视为垃圾, 在确定哪些垃圾可以回收后, 会通过标记清除, 复制, 标记整理, 和分代回收算法进行垃圾回收
	- 两次标记的过程: 
		- 对象在被回收之前, 会调用对象的 `finalize()` 方法; 两次标记, 第一次标记不在"关系网"中的对象. 第二次看该对象是否实现了 `finalize()` 方法, 如果没有实现, 那么就判断该对象可以回收, 否则就把它们放到一个低优先级的队列中, 由虚拟机创建一个低优先级的线程去消费它, 这个时候会进行第二次标记, 如果再次被标记了, 那么就会被回收
	- 垃圾回收的过程: 关于垃圾回收的过程, 主要分为三个阶段, 首先通过可达性算法标记存活对象, 然后根据垃圾回收器选择的垃圾回收算法进行回收内存, 最后可能会进行内存整理, 减少内存碎片. 现在JVM常用分代收集策略, 在年轻代上用复制算法, 在老年代上用标记-清除或者标记-整理算法.
	- 四种垃圾收集算法:
		- 标记-清除算法: 它先把内存中所有需要回收的对象标记出来, 然后回收所有被标记的对象,  缺点为会造成内存碎片
		- 标记-复制算法: 它解决了内存碎片的问题, 但是它把内存划分为相同的两块, 每次只使用其中的一块, 当这一块进行了垃圾回收之后, 就会把剩余存活的对象全部复制到另一块内存上面, 缺点为只能用一半的内存, 成本太高
		- 标记-整理算法: 它把当前存活的对象移向内存的一端, 然后删除边界以外的所有内存, 缺点为移动对象的成本高
		- 分代收集算法: 它根据对象的存活周期把对象分为了年轻代和老年代, 年轻代又分为了Eden区和Survivor区, Survivor区又分为From和To区, 然后在年轻代使用复制算法, 因为新生代里的对象通常生命周期短, 复制的成本低, 老年代用标记-整理算法，因为对象存活率较高
			- 追问为什么要分代收集: 新生代的对象生命周期短，使用复制算法可以快速回收, 同时复制的对象的数量也少, 成本低。老年代的对象生命周期长，使用标记-整理算法可以减少移动对象的成本。

	- 垃圾收集器: 分为分代收集器和分区收集器两种, 代表分别为CMS,    G1和ZGC
		- CMS它是一种低延迟的垃圾收集器, 它使用**多线程的标记-清除算法,** 它的垃圾收集分为四个阶段, 分别是初始标记, 并发标记, 重新标记和清除, 它的优点是垃圾回收线程可以和用户线程并发进行, 缺点是 
			1. 易产生内存碎片, 容易引发Full GC 
			2. 浮动垃圾: 在并发清理阶段, 用户线程仍然工作可能产生垃圾, 如果垃圾产生过多, 导致老年代空间不足, 并发模式失效, 就会Full GC 
		- G1它适合那种大堆场景, 它将堆划分成了很多个大小相同的区域, 每个区域都用来存储不同类型的对象, 它使用**标记-整理算法**, 避免了内存碎片, 同时它的停顿时间(STW)是可控的, 即可以设置每次垃圾回收STW的暂停时间(通过选择性回收部分垃圾多的区域实现)
		- ZGC它也一款低延迟的垃圾收集器, 它最大特点在于它可以把垃圾收集的停顿时间控制在10ms以下, 即使是TB级别的堆也有很低的延迟.  它通过并发标记和重定位避免了大部分的STW时间, 实现了超低的延迟.  适合那种需要超低延迟的场景, 比如金融交易系统等等

		- 详细说一下CMS垃圾回收的过程吧: CMS垃圾回收分为四个阶段, 分别是初始标记, 并发标记, 重新标记和清除.               
			- 在**初始标记**阶段, 标记GC Roots直接可达的对象  (JVM会通过可达性算法, 从GC Roots出发, 标记可以直接到达的对象, 这阶段需要STW, 速度很快);   
			- 然后就进行**并发标记**, 并发标记阶段从初始标记了的对象出发, 遍历所有的对象, 标记所有的可达对象. (可能导致的**问题**: 但是因为它是和用户线程并发进行的, 所以可能会改变对象的引用, 导致超标或者漏标);    
			- 所以接下来就有了**重新标记**, 它用来完成剩余标记工作, 同时也解决并发标记阶段遗留的问题, 这阶段也需要STW;  
			- 最后就是**并发清理**, 垃圾收集线程与用户线程并发执行, 释放内存

		- 关于G1收集器呢: 关于G1收集器, G1在JDK1.7时被引入, 然后再JDK9的时候正式代替CMS成为了默认的垃圾收集器.  G1把堆划分成了许多个相同大小的小区域 Region, 每个区域都可以扮演年轻代或者老年代的角色.  G1还有专门为大对象设计的Region, 叫做Humongous 区.   G1的**垃圾回收流程**大致分为以下几类: 
			- **初始标记**: 标记从GC Roots直接关联的对象
			- **并发标记**: 并发标记阶段从初始标记了的对象出发, 遍历所有的对象, 标记所有的可达对象. 并发标记阶段与用户线程同时进行 
			- **最终标记**: 用来解决并发标记阶段遗留的问题
			- **混合收集**: 在并发标记阶段结束后, G1会计算哪一块区域的回收价值大(就是垃圾多), 然后回收这些区域, 这种方式使得它只回收部分年轻代与老年代, 而不是回收整个堆
			
			- 预测停顿时间: G1在进行垃圾回收的时候仍然选要STW, 但是G1允许用户在JVM启动的时候自己设置一个期望停顿时间, G1会在这个时间内尽可能的完成垃圾收集

		- 三色标记法(减少停顿时间): 
			- 分为三种颜色: 
				- 白色: 未被标记的对象
				- 灰色: 已经被标记的对象, 但是引用对象没有被标记完
				- 黑色: 引用对象也被标记完了的对象
			- 流程: 
				- 初始标记: 标记所有GC Roots根对象, 将根对象和它的直接引用对象标记为灰色
				- 并发标记: 从所有的灰色对象出发, 遍历所有的对象, 标记所有的白色引用对象为灰色, 然后将该灰色对象标记为黑色, 不断重复直到没有灰色对象.    因为应用程序是并发允许的, 所以对象引用可能会变化, 需要使用写屏障来记录引用变更
				- 重新标记: 处理并发标记阶段出现的问题
			
			- 对于出现的漏标问题: 
				- 什么情况会出现漏标: 要满足两个条件: 
					- 并发标记时, 新增了一条从黑色对象到白色对象的引用 **并且** 切断了所有灰色对象到该白色对象的直接或间接的引用
				- 这种情况下白色对象无法标记为存活, 会漏标
			- 解决办法: 
				- CMS使用增量更新: 
					- 在并发标记过程中出现新增引用时, 
					- 把该引用关系记录下来, 在重新标记阶段根据该记录进行判断
				- G1使用原始快照: 
					- 在并发标记过程中当删除灰色对象到白色对象的直接或间接的引用时, 
					- 把该引用关系记录下来, 在重新标记阶段进行判断
			- 多标不用管, 下一次GC就回收了
- 类加载机制: 
	- 了解类加载机制吗: 了解. JVM的操作对象是Class文件.  JVM把Class文件中关于类的数据结构加载到内存中, 然后进行校验, 解析和初始化, 使得它转化为JVM可以直接使用的类型, 这个过程就叫做类加载机制
	- 讲一下类加载的过程: 类加载的过程分为三个阶段, 分别是加载, 连接和初始化
		- 加载就是将类的二进制字节码加载到内存里面, 然后生成对应的Class对象
		- 连接分为三个小的阶段, 分别是验证, 准备和解析
			- 验证是检查类文件是否符合JVM的规范
			- 准备就是为类中的静态变量分配空间并且设置默认值(如果是static final修饰的静态变量, 并且是编译期常量, 会直接赋值代码中指定的值)
			- 解析就是把常量池里面的符号引用替换为直接引用(这一步允许在初始化之后执行)
		- 初始化阶段会执行`<clinit>()` 方法, 给静态代码块和静态变量的初始化, 就是把代码里面的值赋值给静态变量
- 双亲委派模型了解吗:在类加载的时候，系统会⾸先判断当前类是否被加载过。已经被加载的类会直接返回，否则才会尝试加载。加载的时候，⾸先会把该请求委派该⽗类加载器的 `loadClass()` 处理，因此所有的请求最终都应该传送到顶层的启动类加载器 `BootstrapClassLoader` 中。当⽗类加载器⽆法处理时，才由⾃⼰来处理。
	- 从顶层到底层: 启动类加载器->扩展类加载器->应用程序类加载器
	- 好处: 保证了核心类库的安全; 避免了类的重复加载
	- Tomcat破坏了双亲委派模型: 它有一个WebApp类加载器, 先自己加载, 失败了再去找父加载器
- JVM调优: 
	- 服务环境: ParNew + CMS + JDK8
		
		- 1. 问题像C端核心业务每个接口的请求耗时一般有限制在例如100ms以内，C端核心业务在高峰期服务器发生 FullGC，（FullGC的耗时甚至可以达到1s）导致部分请求超时报错，影响用户体验
			- 原因是因为CMS对于老年区使用标记-清除算法, 时间一长造成了大量的内存碎片, 导致了没有足够的连续空间来分配对象, 造成Full GC
			- 解决办法: 可以在业务低峰期手动触发 Full GC(System.gc()), 当触发Full GC时, CMS会退化为单线程的serialOld垃圾回收器, 它使用标记-整理算法, 可以整理堆内存优化掉内存碎片的情况，降低业务高峰期发生FullGC的概率
		
		- 2. 问题是YoungGC 和 OldGC 频繁
			- 原因是因为该服务要求低延迟, 所以为了YoungGC快速完成, 年轻代内存设置小, 就导致了频繁的YoungGC, 连锁反应也导致了大量对象晋升到了老年代, 导致OldGC频繁
			- 解决办法一般就是扩大年轻代内存为原来的3倍
			- (年轻代内存扩大三倍，不代表YGC耗时也会变为三倍，YGC是复制算法，耗时的是复制的阶段，大部分的对象还是被垃圾回收了，所以单次YGC的耗时只是轻微增加)

		- 3. 服务环境 G1 + JDK8
			- 问题是服务YoungGC 频繁
			- 原因是-XX：MaxGCPauseMillis(STW时间) 暂停时间目标参数设置较小，导致JVM自动调整降低年轻代的region
			- 解决办法: 调大-XX：MaxGCPauseMillis 或者 固定年轻代的region的大小
- 线上Full GC频繁或者内存持续上涨咋办: 
	- 我会先看监控确认 Full GC 的频率、耗时、Young GC 是否过于频繁, Old 区占用是否异常, Full GC 后 Old 区是否明显下降等等。这里面关键是观察 **Full GC 后 Old 区是否明显下降**。如果下降，可能是瞬时大对象或 GC 参数不合理；如果不下降，就怀疑内存泄漏。
		- 为什么就怀疑是内存泄漏呢?
			- 因为如果Full GC后Old区占用不下降, 说明大量的对象仍然可达, 需要通过heap dump分析GC Roots引用链
- 内存泄漏了咋办:
	- 首先可以用 `jps -l` 找到目标Java进程PID, 然后我会用 `jstat -gcutil` 实时观察各内存区变化(重点看O(老年区)和FGC(Full GC次数), 如果O持续上涨, 并且FGC增加后O不下降, 那么基本上就是重点问题) 
	- **重点**: 然后进一步可以用 `jmap -dump`(会造成停顿, 不要在线上高峰期用尽量) 导出 heap dump，用 MAT/VisualVM 这些工具去分析 dump文件, 重点看哪些对象占用内存高, GC Roots引用链, 是否有集合类, ThreadLocal这种长期持有的对象等等
- CPU飙高咋办, 线程死循环, 锁竞争就可以用这一套:
	1. `top` 命令, 查看各进程的CPU占用情况, 得到占用CPU高的进程 PID
	2. `top -H -p <pid>` 命令, 可以看到该进程里面各个线程的占用CPU的情况, 找到具体高 CPU 的线程 ID
	3. 先把第二步得到的线程ID转换为16进制
	4. `jstack <PID>` 命令, 用第一步的PID导出线程栈(通过该命令得到的线程nid是16进制的)
	5. `grep 16进制的线程ID` 命令, 从线程栈里面找具体的线程nid(这里看出是不是和GC相关的线程)
	6. 找到线程了, 看栈顶方法和线程的状态. 如果是RUNNABLE, 重点看死循环, 大量计算, 大集合排序等等; 如果是GC相关的线程活跃, 那么就用 jstat -gcutil 和 GC日志(连续GC)判断是否是频繁GC
