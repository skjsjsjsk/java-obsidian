- 项目接口发生OOM如何排查:
	1. 发生OOM后, 首先就是保存现场, 从应用日志, JVM日志中确定OOM发生的具体时间和类型
		1. 如何看类型: 直接看异常的最后一行, 像  `java.lang.OutOfMemoryError: Java heap space`
		   那么就是 `Java heap space(Java堆空间不足, 重点排查大对象或内存泄漏)`; 
		   还有 `Metaspace(重点排查动态生成类过多或 ClassLoader 泄漏)`; 
		   `Direct buffer memory(重点排查 NIO、Netty、直接内存和缓冲区释放); 
		   `unable to create new native thread(重点排查线程池、线程泄漏和操作系统线程限制)`
	2. 然后以OOM的时间点为中心, 查询网关和应用访问日志, APM, 看哪些接口的QPS, 响应时间, 内存占用出现异常, 如果日志里有线程名, Trace ID等等, 就可以定位到具体的接口和代码了
	3. 如果日志无法确定接口, 那么就可以结合线程Dump, Heap Dump, GC日志进一步分析: 
		1. 线程Dump看当时有哪些请求在执行以及是否有线程堆积
		2. Heap Dump 用MAT查看大对象, GC Roots引用链
		3. GC 日志用于判断是单次大对象, 并发过高还是长期内存泄漏
	4. 确定好接口后, 检查接口代码, 像SQL没有分页, 一次查询几十万条数据, `ThreadLocal` 使用后没有调用 `remove()` 等等
	5. 根据问题进行解决, 增加分页, 游标处理; 在 `finally` 中调用 `remove()` 等等
	```
	面试时可以简化为：
		1. **确认 OOM 类型**：堆内存、元空间、直接内存还是线程不足。
		2. **保留现场**：Heap Dump、GC 日志、线程栈、监控数据。
		3. **定位关联接口**：结合 APM、访问日志、QPS、请求大小和调用时间。
		4. **分析具体原因**：用 MAT 查大对象、对象数量和 GC Roots 引用链。
		5. **修复并验证**：分页、流式处理、限制并发、清理引用，再通过压测验证。
	```
- 如何使用MAT呢: 
	1. 生成Heap dump, 导入MAT中, 等待解析完成
	2. 执行 `Leak Suspects Report`, 会给出疑似内存泄漏的点, 像某个对象占用了大部分堆内存
	3. 使用 `Histogram(根据类进行查找的)` 找异常类型, 可以找到什么类型的对象最多
	4. 查看 `Dominator Tree`, 并按照 `Retained Heap` 从大到小排序(Retained Heap是该对象被回收可以释放多少内存的大小), 可以通过这个找到大对象
	5. 找到大对象后, 右键选择 `Path to GC Roots` , 排除弱引用, 进行分析OOM的原因

- SpringMVC 与 SpringBoot 的区别: 
	- SpringMVC是Web MVC框架, 主要解决请求接收, 参数绑定, 业务调用等问题. 核心组件是 `DispatcherServlet`, 常用注解包括 `@Controller`、`@RequestMapping`、`@RestController`
	- SpringBoot是一个用于快速创建和运行 Spring 应用的开发框架, 主要通过自动配置, 约定优于配置, Starter依赖等简化 Spring 项目的搭建与部署
- MySQL的DDL, DML, DQL, TCL: 
	- DDL: 不涉及数据, 涉及表的结构 , 像CREATE, ALTEAR等等. DDL会隐式提交当前事务, 执行后无法回滚
	- DML: 表中的记录, update, insert, delete
	- DQL: 查询数据, select
	- TCL: 事务控制语言, 像COMMIT, ROLLBACK, SAVEPOINT(事务中设置保存点, 实现部分回滚)
- Redis主节点加锁成功后宕机, 切换到从节点时是否可能没用同步锁信息: 
	- 可能的, 因为主从复制是异步的
	- 具体来说: 
		1. 客户端A向主节点M发起加锁请求, 然后成功加锁, 还没同步给从节点
		2. 宕机了, 哨兵节点检测到M下线, 提升N为新的主节点
		3. 客户端B向N请求加锁, 成功加锁(因为key不存在)
		4. 现在就导致了客户端A, B都有锁, 它们同时操作共享资源, 会导致数据不一致
	- ==脑裂:== 脑裂会加剧这个问题, 
		1. 脑裂是由网络分区导致哨兵与旧主节点失联, 而客户端仍然可能连接旧主节点. 
		2. 然后哨兵选取出新的主节点
		3. 此时存在两个主节点, 可能会导致出现上面的客户端A, B同时加锁成功的场景
	- 防范: 
		- A: 红锁算法: 部署多个完全独立互不相关的Redis主节点, 客户端依次向这些节点加锁, 半数以上成功才算加锁成功并且总耗时小于锁的有效期
		- B: `WAIT` 命令, 会强制等待数据同步到指定数量的从节点上面, 保证数据一致

- 微服务架构中的负载均衡是如何实现的: 
	- 两类: 
		- 服务端负载均衡: 客户端先请求Nginx, 网关等等, 再由它转发到后端实例
		- 客户端负载均衡: 服务实例注册到Nacos等注册中心, 调用方获取服务实例列表, 根据负载均衡的策略拉取需要的实例
- MySQL中RR加MVCC加临建锁基本解决了幻读, 它的性能还比串行化高, 那为什么还需要串行化呢? 
	- 首先就是因为幻读只是并发异常中的一种. 你像RR下两个事务读取相同的状态但是更新不同的记录, 破坏了约束. 这叫做写偏斜
- 不同的垃圾回收器对JDK版本的要求: 
	- JDK8: 常见Parallel GC, 也支持CMS和G1
	- JDK9: G1成为默认
	- JDK11: ZGC以实验特性被引入
	- JDK14: CMS被移除
	- JDK15: ZGC成为正式的生产特性
	- JDK21: 引入分代ZGC
- Redis常见的部署模式: 
	- 四种: 
		1. 单机模式: 本地部署
		2. 主从复制: 主节点写, 从节点读, 但是如果出现故障就会宕机, 本身不能自动故障转移
		3. Sentinel 哨兵模式: 在主从基础上增加哨兵节点, 可以监控, 选主加自动切换
		4. Cluster集群模式: 通过槽位分片, 解决容量和高可用问题
- Java Concurrent包:

		- 并发容器：`ConcurrentHashMap`、`CopyOnWriteArrayList`
