# 防止超卖和一人一单

## 第一版
- 对于一人一单: 可以直接去数据库查询是否下过单. 如果有对应优惠券的订单ID, 那么就拒绝请求. 同时为了防止同一个用户重复下单, 要使用分布式锁
- 对于库存超卖: 在更新的时候加上 ` where stock > 0`保证不超卖
- 但是该方案高并发下所有请求会直接打到数据库, 而且大量的数据库查询请求和更新数据以及锁竞争都集中在数据库, 严重影响秒杀业务的性能
## 第二版
- 然后因为我当前项目使用了Redis, 而Redis是基于内存的, 读取速度很快, 我就想着能否把下单资格的校验放到Redis中完成

- 秒杀流程的最终优化: 
	- 我这个优化为, 核心使用 `使用Lua脚本进行资格校验, 异步使用消息队列去处理MySQL库存扣减和订单生成, 提高并发性能`
	- 因为扣减库存, 生产订单, 这些步骤都是对MySQL进行操作, 但是实际上对于秒杀来说, 当判断你有秒杀资格的那一步起, 你就秒杀成功了, 剩下的步骤就是为了实现秒杀, 所以完全可以异步来执行, 提高性能
	- 流程: 
		- **资格判断**: 当用户请求进来以后, 我会先做资格判断, 先查是否在秒杀券活动的时间内, 判断用户有无参与资格, 然后就执行Redis的Lua脚本, 原子的判断库存是否充足, 用户是否下过单, 通过的话, 就先在Redis里面预扣库存, 并把用户写入下单集合
		- **异步处理**: 拿到资格后, 我生成一个全局订单ID, 然后异步发送Kafka消息(`包含 orderId、userId 和 voucherId`), 让Kafka消费者去执行数据库和订单创建.   在消费者端, 我做了两层防护, 一层是先按userId加Redisson锁, 防止同一个用户并发消费, 另一层是在**事务里**再次校验**数据库是否已经下单**, 并且用`where 库存 > 0`的条件更新兜底防超卖, 扣库存成功, 才保存订单. 这样在数据库层还有一次兜底, 保证不超买, 不生产重复订单
		- **失败补偿**: 如果Kafka发送失败, 或者消费过程失败, 我会执行Redis回滚脚本, 把预占库存和用户资格释放掉
	- 追问: 
		- **面试官如果问“你这里的下单资格是什么”**: 
		- 你可以直接说：
		- 我这里的下单资格有三层含义：
			1. 活动时间上有资格，也就是当前时间在秒杀开始和结束时间之间
			2. 库存上有资格，也就是 Redis 里的秒杀库存还大于 0
			3. 用户维度上有资格，也就是这个用户还没有抢过这个券
		- 只有这三个条件都满足，我才允许发送 Kafka 下单消息。
