- 项目接口发生OOM如何排查:
	1. 发生OOM后, 首先就是保存现场, 从应用日志, JVM日志中确定OOM发生的具体时间和类型
		1. 如何看类型: 直接看异常的最后一行, 像  `java.lang.OutOfMemoryError: Java heap space`
		   那么就是 `Java heap space(Java堆空间不足, 重点排查大对象或内存泄漏)`; 
		   还有 `Metaspace(重点排查动态生成类过多或 ClassLoader 泄漏)`; 
		   `Direct buffer memory(重点排查 NIO、Netty、直接内存和缓冲区释放); 
		   `unable to create new native thread(重点排查线程池、线程泄漏和操作系统线程限制)`
	2. 然后以OOM的时间点为中心, 查询网关和应用访问日志, APM, 看哪些接口的QPS, 响应时间, 内存占用出现异常, 如果日志里有线程名, Trace ID等等, 就可以定位到具体的接口和代码了
	3. 如果日志无法确定接口, 那么就可以结合线程Dump, Heap Dump, GC日志进一步分析: 
		1. 线程Dump看当时有哪些请求在执行以及是否有线程堆积
		2. Heap Dump 用MAT查看大对象, GC Roots引用链
		3. GC 日志用于判断是单次大对象, 并发过高还是长期内存泄漏
	4. 确定好接口后, 检查接口代码, 像SQL没有分页, 一次查询几十万条数据, `ThreadLocal` 使用后没有调用 `remove()` 等等
	5. 根据问题进行解决, 增加分页, 游标处理; 在 `finally` 中调用 `remove()` 等等
	```
	面试时可以简化为：
		1. **确认 OOM 类型**：堆内存、元空间、直接内存还是线程不足。
		2. **保留现场**：Heap Dump、GC 日志、线程栈、监控数据。
		3. **定位关联接口**：结合 APM、访问日志、QPS、请求大小和调用时间。
		4. **分析具体原因**：用 MAT 查大对象、对象数量和 GC Roots 引用链。
		5. **修复并验证**：分页、流式处理、限制并发、清理引用，再通过压测验证。
	```

- 如何使用MAT呢: 
	1. 生成Heap dump, 导入MAT中, 等待解析完成
	2. 执行 `Leak Suspects Report`, 会给出疑似内存泄漏的点, 像某个对象占用了大部分堆内存
	3. 使用 `Histogram(根据类进行查找的)` 找异常类型, 可以找到什么类型的对象最多
	4. 查看 `Dominator Tree`, 并按照 `Retained Heap` 从大到小排序(Retained Heap是该对象被回收可以释放多少内存的大小), 可以通过这个找到大对象
	5. 找到大对象后, 右键选择 `Path to GC Roots` , 排除弱引用, 进行分析OOM的原因

- Java版本的特性: 
	- Java7: 
		- `switch`支持字符串; 
		- **`try-with-resources`自动关闭资源**
		- **多异常捕获: `catch(A | B e)`**
		- **泛型菱形语法: `<>`**
	- Java8: 
		- Lamba表达式
		- 函数式接口
		- Stream API
		- 接口的 `defult` 和 `static` 方法
		- CompletableFuture
		- 永久代被元空间 Metaspace 替代
		- 新时间的API: `LocalDateTime`, `LocalDate` 等
	- Java9: 
		- 集合工厂方法: `List.of()`、`Set.of()`、`Map.of()`
		- 接口支持 `pr`
