## 第一版
- 对于一人一单: 可以直接去数据库查询是否下过单. 如果有对应优惠券的订单ID, 那么就拒绝请求. 同时为了防止同一个用户重复下单, 要使用分布式锁
- 对于库存超卖: 在更新的时候加上 ` where stock > 0`保证不超卖
- 但是该方案高并发下所有请求会直接打到数据库, 而且大量的数据库查询请求和更新数据以及锁竞争都集中在数据库, 严重影响秒杀业务的性能
## 第二版
- 然后因为我当前项目使用了Redis, 而Redis是基于内存的, 读取速度很快, 我就想着能否把下单资格的校验放到Redis中完成, 正好Redis有Lua脚本, 执行是原子性的, 满足我的要求
- 所以秒杀流程的最终优化: 
	- 我这个优化为, 核心使用 `Lua脚本进行资格校验 + Kafka异步下单`, 
	- 因为扣减库存, 生产订单, 这些步骤都是对MySQL进行操作, 但是实际上对于秒杀来说, 当判断你有秒杀资格的那一步起, 你就秒杀成功了, 剩下的步骤就是为了实现秒杀, 所以完全可以异步来执行, 提高性能
	- 流程: 
		- **资格判断**: 当用户请求进来以后, 先查秒杀券是否存在, 是否在秒杀券活动的时间内,  判断用户有无参与资格, 然后就执行Redis的Lua脚本, 原子的判断库存是否充足, 用户是否下过单等等, 通过的话, 就直接在Redis里预扣库存并且把用户写入下单集合, 标记占用资格.  然后生成一个全局订单ID, 然后立即发送Kafka消息(`包含 orderId、userId 和 voucherId`), 接口迅速返回
		- **异步处理**: Kafka消费者去执行数据库库存扣减和订单创建.   
			- 在消费者端, 我做了两层防护,  (**消费者端做幂等, 经过下面两层保证, 即使重复消费了消息, 也不会重复生成订单**)
				- 一层是先按userId加Redisson锁, 防止同一个用户并发消费,
				- 另一层是在**事务里**再次校验**数据库是否已经下单**, 并且用`where 库存 > 0`的条件更新兜底防超卖, 扣库存成功, 才保存订单. 
			- 这样在数据库层还有一次兜底, 保证不超买, 不生产重复订单
		- **失败补偿**: 
			- 如果Kafka发送失败, 或者消费过程失败, 我会执行Redis回滚脚本, 把预扣的库存和用户资格释放掉, 避免Redis与数据库结果不一致
	- 追问: 
		- **面试官如果问“你这里的下单资格是什么”**: 
		- 你可以直接说：
		- 我这里的下单资格有三层含义：
			1. 活动时间上有资格，也就是当前时间在秒杀开始和结束时间之间
			2. 库存上有资格，也就是 Redis 里的秒杀库存还大于 0
			3. 用户维度上有资格，也就是这个用户还没有抢过这个券
		- 只有这三个条件都满足，我才允许发送 Kafka 下单消息。
## 为什么有了Redis预扣，还需要数据库二次校验？
- 三个原因: 
	1. 第一，保证幂等性。 Kafka采用的是至少一次(at-least-once) 投递语义，可能会出现消息重复消费的情况。虽然有Redisson锁防止并发，但如果消费者在处理成功后、提交Offset前宕机，Kafka会重新投递消息。此时数据库中订单已经存在，二次校验可以防止重复创建订单。
	2. 第二，防止超卖的最终兜底。 数据库层的 stock > 0 乐观锁是防止超卖的最后一道防线。即使Redis预扣成功，但在数据库扣减时，可能因为以下原因导致库存不足：
		- Redis数据丢失（主从切换）
		- 管理员手动调整库存
		- 其他渠道消耗了库存
	3.  第三，数据库是数据的最终权威来源。 Redis只是缓存层，用于提升性能和快速过滤，而数据库的ACID事务才能保证业务规则的最终正确性。这种'Redis快速过滤 + 数据库精确校验'的双层设计，既保证了高并发下的性能，又保证了数据的一致性
## 如何保证数据一致性
- Kafka 发送失败 → 回滚 Redis
- 消费失败 → 回滚 Redis
- 保证 Redis 和数据库的最终一致性

# 缓存优化
## 缓存击穿
- 对于缓存击穿, 它是热点key过期问题, 我想到了两种方案, 分别是 `互斥锁` 和 `使用逻辑过期`
- 互斥锁: 
	- 它是当大量请求访问数据库时, 给一个请求加锁去重建缓存, 其他请求阻塞
	- 因为锁竞争, 所以会一定程度上影响性能, 外界表现为不可用, 但是它保证了强一致性, 同时读取到的数据也是最新的
- 逻辑过期: 
	- 它就是对于热点数据不设置TTL, 而是设置一个逻辑过期时间
	- 当请求到来时, 获取key时会检查时间字段, 判断是否过期. 如果过期, 就让一个线程去加锁更新缓存, 其他请求先返回旧值
	- 它因为可以返回旧数据, 线程无需等待, 所以性能较好, 牺牲短暂的数据一致性，换取高可用性
- 因为这是我觉得这算是一个社交类型的数据, 对于一致性没有那么高的要求, 暂时的旧信息可以接受, 所以选择了逻辑过期方案
- 测试: 我手动修改数据库数据, 使得数据不一致, 然后使用逻辑过期的情况下, 用Jmeter进行压力测试时, 4s 内 4000个线程的QPS是1000, 查看日志可以看到只有一次查询数据库重建缓存的过程
## 缓存穿透
- 对于缓存穿透, 它是有大量恶意请求, 使用数据库不存在的商铺ID去查询, 导致请求直接打到数据库的问题, 我想到的方案有 `缓存空值` 和 `布隆过滤器`
# 数据一致性
- 我保证的是缓存和数据库的最终一致性, 因为店铺的信息一般读多写少
- 流程为 `Cache Aside + Kafka异步补偿`: 先更新数据库再删缓存, 删除失败就Kafka补偿重试, 超过阈值就记录错误日志然后告警 + 人工介入, 保证最终一致性
	- 当用户修改店铺信息时, 我会先在事务里更新数据库, 然后再删除店铺的缓存交给补偿服务处理. 补偿服务会尝试删除缓存, 如果删除成功, 那么后续请求会从数据库中查询到最新值重建缓存; 
	- 如果删除失败, 那么就会把删除动作封装为一个Kafka消息发送出去, 里面包含缓存 key 和 重试次数. 消费者收到消息后会重试删除, 如果重试超出次数那么就记录错误日志并且人工介入. 这样即使Redis短暂故障, 恢复后也能自动完成缓存删除, 保证最终一致性
## 为什么是删除缓存而不是更新
- 因为该数据很少被查询, 减少不必要的缓存更新

# Kafka
## 消息不重复消费
- 按照至少一次投递---对应消息不丢失 At Least once 对于消息重复传递不敏感的场景
	- 消息不会丢失
	- 消息会重复投递
- 通过在业务层做幂等设计来解决:
	- 在创建订单时, 数据库层会查询是否已有订单, 做一人一单校验, 防止创建重复订单
	- 使用全局订单ID, 发送消息时携带该 `orderId`, 即使重复发送消息, 也因为订单ID相同不消费
	- Redisson 锁防止并发创建订单
## 消息不丢失
### 生产者端
- 首先我设置了 `acks=all` , 保证了当发送消息以后, leader收到后, 所有的ISR副本同步成功才会返回响应
- 然后在业务层面, 当消息发送后, 如果发送失败了, 就会捕获异常同时执行Redis回滚, 防止订单丢失
### Broker端
- 我设置了分区副本=3, `min.insync.replicas=2` 保证leader副本挂了, 也可以选举follow副本作为新的leder副本, 保证消息的接收
### 消费者端
- 自动提交offset
- 消费失败执行Redis回滚

## 如何保证顺序消费
### 生产者端
- 发送消息时使用 `userId` 作为key, 相同的key会进入同一个partition, 而同一个partition内的消息是有序的
### 消费者端
- 单线程消费每个partition
- 此外也使用Redisson分布式锁防止并发处理同一个用户的消息
# 超时订单自动关闭
- `Spring Task定时任务 + 批量处理 + Kafka补偿重试`
- 首先就是我设置定时任务每分钟执行一次。 计算30分钟前的时间点，从MySQL数据库中查询所有创建时间早于该时间点且状态为'未支付'的订单。每次只查询100条，避免一次性处理太多数据导致内存溢出或长时间锁表。
- 其次, 逐个处理订单并保证幂等性。 对于每个订单，我会先从数据库查询最新状态，然后用乐观锁更新：UPDATE SET status=CANCELLED WHERE id=? AND status=UNPAID。这样即使用户在关单过程中完成了支付，也不会误取消订单。更新成功后，回补库存，最后释放Redis中的抢购资格和预扣库存.  `为了保证取消订单和回补库存的原子性, 所以在事务中进行`
- 然后, 对于超时订单自动关闭, 我做完后进行了code review, 发现没有释放用户在Redis中的下单资格, 导致取消订单后无法再次下单.  所以为了支持取消后重新下单, 我做了两层处理:  第一层在数据库层的校验中排除了未支付的订单;  第二层因为Redsi中使用的是Hash结构存储的下单资格, 所以关单时顺便会删除用户的资格记录, 使得用户可以重新下单
- 最后Kafka补偿保证最终的一致性. 如果关单过程的某一步失败了, 那么就会发送Kafka补偿消息, 最多允许重试3次, 3次过后还没成功就记录错误日志, 人工介入

## 方案选择
- 我在处理超时订单自动关闭的时候查询了几种常用的方案
- 方案1: 每隔固定时间执行一个定时任务, 扫描 MySQL 数据库取出未支付且超时的订单
	- 优点是实现简单, 缺点是数据量很大的时候, 查询会给数据库造成一定的压力, 可以通过建索引解决
- 方案2: 使用RocketMQ的延迟消息, 在订单创建的时候发送延迟消息, 一定时间后, 消息被消费关单
	- 优点是通过消息队列的延迟消息, 实现了解耦
	- 缺点是, 可能会有大量的无效调度, 就是很多消息的订单状态都是已支付的;  还有就是因为使用了消息队列, 所以极端情况下, 仍然可能会重复消费或者消息丢失, 可能导致多次错误关闭或者订单未关闭
- 方案3就是使用Redis的过期监听, 为每一个订单设置一个TTL, 接收key的过期消息执行关单操作
	- 通过在redis.conf中配置开启过期监听, 这样就可以监听key的过期消息了
	- 优点是因为Redis的高性能, 所以设置key以及消费key上的时间是很短的
	- 缺点是因为Reids的key过期策略是, 定时任务离线扫描删除或者访问键的时候惰性检查键是否过期.   所以因为该策略的原因, 我们的监听事件无法第一时间消费这个key, 会有一定延迟
## 会重复关闭订单导致重复增加库存吗
- 不会, 因为关单执行的SQL是 `update orders set status = '取消' where id = ? and status = '未支付'`. 只有状态更新成功才会增加库存
