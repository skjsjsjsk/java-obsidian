### Redis 的 SETNX

- `SETNX` 的全称是 **SET if Not eXists**
- 含义是：**只有 key 不存在时，才会设置成功**
- 如果 key 已经存在，设置失败
- 返回值一般可以理解为：
  - `1`：设置成功
  - `0`：设置失败，说明 key 已存在

### 用它实现幂等的思路

- 客户端请求时携带一个**全局唯一的幂等号**，比如订单号、请求流水号
- 服务端先执行：
  - `SETNX idempotent:请求号 1`
- 如果返回 `1`，说明是第一次请求，可以继续执行业务
- 如果返回 `0`，说明这个请求已经处理过了，直接返回成功或提示重复提交

### 更推荐的写法

不要单独用 `SETNX`，而是直接用 Redis 的原子命令：

```bash
SET key value NX EX 60
```

比如：

```bash
SET idempotent:123456 1 NX EX 60
```

含义是：

- `NX`：只有 key 不存在时才设置
- `EX 60`：60 秒后自动过期

### 为什么要加过期时间

- 防止这个幂等标记一直存在，导致后续无法再次操作
- 避免服务异常后 key 永久残留
- 释放 Redis 内存

### 为什么不建议 `SETNX` 和 `EXPIRE` 分开写

比如这样：

```bash
SETNX idempotent:123456 1
EXPIRE idempotent:123456 60
```

有风险：

- 如果 `SETNX` 成功了
- 但在执行 `EXPIRE` 之前服务挂了
- 那么这个 key 就**没有过期时间**
- 会导致幂等标记长期存在，产生误判

所以面试里最好说：

- `SETNX` 可以实现幂等
- 但生产中更推荐使用 `SET key value NX EX timeout`，因为它把“判重”和“设置过期时间”做成了**原子操作**

### 适用场景

- 防止重复下单
- 防止表单重复提交
- 防止接口因为重试机制被重复消费
- 分布式环境下的简单幂等控制

### 要注意的问题

- Redis 幂等标记适合做**短时间防重**
- 如果是“必须永久保证不重复”，更稳妥的方案通常还是：
  - 数据库唯一约束
  - 去重表
- 因为 Redis 数据可能过期、丢失，不能完全替代数据库最终一致性的约束

## 什么是数据库本地事务

- 数据库本地事务指的是：一组 SQL 操作，要么**全部成功**，要么**全部失败回滚**
- 它的控制范围只在**单个数据库**内部，不涉及多个数据库、多个服务、多个系统之间的协调
- 比如在 MySQL 中，使用 `begin / commit / rollback` 控制的一次事务，就是本地事务

---

## 举个例子

比如转账：

- A 账户减 100
- B 账户加 100

这两个操作如果都在**同一个数据库**里执行，那么就可以放在一个本地事务中：

```sql
BEGIN;
UPDATE account SET money = money - 100 WHERE id = 1;
UPDATE account SET money = money + 100 WHERE id = 2;
COMMIT;
```

如果中间出错了：

```sql
ROLLBACK;
```

这样就能保证：

- 要么两条 SQL 都成功
- 要么都不生效

这就是数据库本地事务

---

## 本地事务的特点

### 1. 依赖数据库自身实现

- 比如 MySQL InnoDB 通过：
  - undo log
  - redo log
  - 锁机制
  - MVCC
- 来保证事务的原子性、一致性、隔离性、持久性

### 2. 只适用于单库场景

- 如果你的业务只操作一个库中的数据
- 那数据库本地事务是最简单、最可靠的方案

### 3. 性能和一致性通常比较好

- 因为不需要跨网络协调
- 也不需要引入额外的事务管理器
- 相对分布式事务来说，实现更简单，成本更低

---

## 和分布式事务的区别

### 本地事务

- 事务只在一个数据库里
- 由数据库自己保证一致性
- 典型场景：单体应用、单库操作

### 分布式事务

- 一个业务操作会涉及：
  - 多个数据库
  - 多个服务
  - 消息队列
  - 第三方系统
- 这时一个数据库的本地事务就不够了
- 需要通过：
  - 2PC
  - TCC
  - 本地消息表
  - 最大努力通知
  - Seata
等方案保证最终一致性

---

## 一个典型面试点

面试官有时会问：

**“Spring 的事务是不是分布式事务？”**

你可以答：

- 不是，Spring 默认的 `@Transactional` 管理的通常是**数据库本地事务**
- 它本质上还是基于单个数据源的事务控制
- 如果一个业务涉及多个服务，单靠 `@Transactional` 是解决不了分布式一致性问题的

---

## 一句话总结

- **数据库本地事务，就是由单个数据库自身提供支持、只作用于单库操作范围内的事务。**

    private StringRedisTemplate redisTemplate;

        if (idempotentKey == null || idempotentKey.isEmpty()) {
            throw new IllegalArgumentException("幂等号不能为空");
        }

        // SETNX + 过期时间，原子操作

        // 设置失败说明key已存在，是重复请求
        if (Boolean.FALSE.equals(success)) {
            throw new IdempotentException(idempotent.message());

        try {

            if (isSystemException(e)) {

            }

# 一、这三段代码整体是在做什么

这是一套基于 **Spring AOP + 自定义注解 + Redis SETNX** 实现接口幂等的代码。

它的核心思路是：

- 先定义一个注解 `@Idempotent`
- 在需要防重复提交的方法上加这个注解
- AOP 在方法执行前拦截它
- 从请求头或者请求参数中取出幂等号
- 用 Redis 做一次“是否第一次请求”的判断
- 如果是第一次，就执行业务逻辑
- 如果不是第一次，就直接拦截，防止重复执行

这其实就是你之前笔记里写的：

- Redis 的 `SETNX`
- 更准确地说，在 Spring 里这里用的是：
  - `SET key value NX EX time`
  - 也就是“**不存在才设置 + 同时设置过期时间**”

# 二、第一段代码分析：`@Idempotent` 注解

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {

    // 幂等号的来源
    IdempotentKeySource source() default IdempotentKeySource.HEADER;

    // 幂等号在Header或参数中的名称
    String key() default "Idempotency-Key";

    // 幂等记录的过期时间，单位秒，默认1小时
    long expireSeconds() default 3600;

    // 重复请求时的提示信息
    String message() default "重复请求，请稍后再试";
}
```

## 1. 这是一个什么东西

这是一个**自定义注解**，名字叫 `Idempotent`。

给方法打上这个注解，相当于告诉系统：

- 这个方法需要进行幂等校验
- 幂等号怎么取
- Redis 里的防重记录存多久
- 重复请求时返回什么提示

---

## 2. 每个注解元信息是什么意思

### `@Target(ElementType.METHOD)`

表示这个注解只能加在**方法**上。

也就是说它的使用方式应该像这样：

```java
@Idempotent
public String createOrder() {
    ...
}
```

不能加在类、字段这些地方。

---

### `@Retention(RetentionPolicy.RUNTIME)`

表示这个注解在**运行时仍然保留**。

为什么必须是 `RUNTIME`？

- 因为 AOP 是在程序运行期间拦截方法的
- 它要在运行时拿到方法上的 `@Idempotent` 注解内容
- 如果不是运行时保留，AOP 就读不到这些配置

这个点是面试里经常可以顺手提一句的。

---

## 3. 注解里的属性分别干什么

### `source()`

```java
IdempotentKeySource source() default IdempotentKeySource.HEADER;
```

表示幂等号从哪里取。

默认从请求头里取，也就是：

- 默认认为客户端会在 HTTP Header 里传一个幂等号

比如：

```http
Idempotency-Key: 123456789
```

---

### `key()`

```java
String key() default "Idempotency-Key";
```

表示取值时使用的字段名。

如果是 `HEADER` 模式：

- 就表示请求头名字

如果是 `PARAMETER` 模式：

- 就表示参数名字

这个设计挺灵活的，因为不同接口的幂等号字段名可能不一样。

---

### `expireSeconds()`

```java
long expireSeconds() default 3600;
```

表示 Redis 中这个幂等标记多久过期，默认 1 小时。

为什么要有过期时间？

- 防止 key 永久存在
- 防止 Redis 内存一直增长
- 给请求重试预留时间窗口
- 防止系统异常时标记长期不释放

---

### `message()`

```java
String message() default "重复请求，请稍后再试";
```

表示当请求被识别为重复请求时，提示什么信息。

这个设计也比较好，因为不同接口可能需要不同文案。

- 如果幂等号为空，直接报错

因为如果为空：

- 所有请求可能都共用同一个 Redis key
- 或者根本没法做防重判断
- 会导致幂等控制失效甚至误伤


```java

```

## 第三步：用 Redis 做原子判重

```java
Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(redisKey, "1", idempotent.expireSeconds(), TimeUnit.SECONDS);
```

这一句是整个幂等实现的关键。

它等价于 Redis 命令：

```bash
SET key value NX EX seconds
```

也可以理解成：

- 如果 key 不存在，就设置成功
- 同时设置过期时间
- 如果 key 已存在，就设置失败

这里返回值的含义：

- `true`：说明第一次请求
- `false`：说明重复请求

为什么这句很重要？

因为它是**原子操作**：

- “判断 key 是否存在”
- “设置 key”
- “设置过期时间”

这三件事一次性完成，不会出现并发竞态问题。

这比下面这种写法安全：

```java
SETNX key value
EXPIRE key 3600
```

因为分开写的话，中间宕机会导致没有过期时间。

---

## 第四步：重复请求直接拦截

```java
if (Boolean.FALSE.equals(success)) {
    throw new IdempotentException(idempotent.message());
}
```

如果 Redis 设置失败，说明这个幂等号已经处理过了。

于是直接抛异常：

- 不再执行后续业务逻辑
- 达到防止重复提交的目的

这里用了：

```java
Boolean.FALSE.equals(success)
```

这种写法比 `success == false` 更稳一点，因为可以顺带避免空指针问题。

---

## 第五步：第一次请求，执行业务逻辑

```java
try {
    return joinPoint.proceed();
}
```

如果前面判定通过，就执行原方法。

也就是：

- 真正的创建订单
- 支付
- 提交表单
- 发起转账
等业务逻辑

---

## 第六步：异常处理

```java
catch (Exception e) {
    // 系统异常删除幂等号，允许重试；业务异常保留幂等号
    if (isSystemException(e)) {
        redisTemplate.delete(redisKey);
    }
    throw e;
}
```

这一段设计是这份代码里比较有思考的一部分。

它的逻辑是：

- 如果执行过程中抛异常了
- 判断这是系统异常还是业务异常
- 如果是系统异常，就把 Redis 的幂等 key 删掉，让客户端可以重试
- 如果是业务异常，就保留 key，不允许重复提交

---

# 七、为什么“系统异常删除 key，业务异常保留 key”

这其实是幂等设计中的一个关键点。

---

## 1. 系统异常删除 key

比如：

- 数据库连接超时
- 网络异常
- Redis 短暂抖动
- 服务内部 NPE
- 下游服务不可用

这些情况通常意味着：

- 这次请求没有被正确处理完
- 用户应该有机会重新发起请求

所以把 key 删掉，允许重试，是合理的。

---

## 2. 业务异常保留 key

比如：

- 订单已经支付
- 库存不足
- 参数不合法
- 当前状态不允许操作

这种异常通常表示：

- 这个请求已经被“处理过”了
- 业务上已经得出了明确结果
- 再重试也没意义，甚至可能导致重复业务处理

所以应该保留幂等标记，防止重复请求继续进来。

---

## 3. 但这里有一个值得你注意的点

这套逻辑不是绝对标准，而是**依赖业务语义**。

有些场景下：

- 业务异常也应该允许重试
- 比如“库存不足”可能稍后补货后可重试
- “参数错误”通常不该占用幂等号
- “用户余额不足”以后充值后也许还能重试

所以这块要看业务，不是所有业务异常都必须保留 key。

换句话说，这段代码体现的是一种常见策略，但不是唯一正确答案。

# 八、辅助方法分析

---

## 1. `extractKey`

```java
private String extractKey(ProceedingJoinPoint joinPoint, Idempotent idempotent) {
    if (idempotent.source() == IdempotentKeySource.HEADER) {
        HttpServletRequest request = getHttpServletRequest();
        return request.getHeader(idempotent.key());
    }
    // PARAMETER模式：从方法参数中按名称提取
    return getParameterValue(joinPoint, idempotent.key());
}
```

这个方法的作用就是：

- 根据注解配置，决定去哪里拿幂等号

### 如果是 `HEADER`

就从请求头拿：

```java
request.getHeader(idempotent.key())
```

比如：

```java
request.getHeader("Idempotency-Key")
```

### 如果是 `PARAMETER`

就从方法参数中按参数名提取。

不过这里你要注意：

- `getParameterValue(joinPoint, idempotent.key())` 这个方法在你给的代码里**没展示出来**
- 所以这段代码目前不是完整可运行版本
- 但从语义上能看出来，它应该是：
  - 获取目标方法参数名
  - 再根据参数名找到对应参数值

---

## 2. `isSystemException`

```java
private boolean isSystemException(Exception e) {
    // BusinessException是业务异常，其他都当作系统异常处理
    return !(e instanceof BusinessException);
}
```

这个方法的意思是：

- 如果异常不是 `BusinessException`
- 那就认为它是系统异常

这个分类逻辑很简单直接。

也就是说当前代码把异常分成两类：

- `BusinessException`：业务异常
- 其他全部：系统异常

这是项目里很常见的一种约定式设计。

---

## 3. `getHttpServletRequest`

```java
private HttpServletRequest getHttpServletRequest() {
    ServletRequestAttributes attrs =
        (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
    return attrs.getRequest();
}
```

这个方法是从当前线程上下文中获取 `HttpServletRequest`。

为什么能拿到？

因为在 Spring Web 环境里：

- 当前请求的信息会绑定到线程上
- 通过 `RequestContextHolder` 可以取到当前请求上下文

这是 Spring 里获取当前请求对象的常见方式。

不过这里也有一个小风险：

- 如果当前方法不是在 HTTP 请求线程中执行
- `attrs` 可能为空
- `attrs.getRequest()` 可能报空指针

但按照这个切面的使用场景，应该默认就是拦截 Controller 或 Web 请求相关方法，所以通常没问题。

扩展性比较好。

# 十、这套方案的缺点和注意点

这部分如果你能讲出来，面试官会觉得你不是只会“看懂代码”，而是真的理解它。

---

## 1. Redis 幂等更适合“短时间防重”

因为 Redis key 会过期。

这意味着：

- 它适合防止用户短时间内重复提交
- 但不适合做永久性的业务唯一约束

比如“订单不能重复创建”这种强约束，最终还是更应该依赖：

- 数据库唯一索引
- 去重表

Redis 更像是第一层防线，不是最终兜底。

---

## 2. 如果业务执行成功，但返回前服务挂了，会怎样

这是一个经典问题。

流程可能是：

- Redis key 设置成功了
- 业务已经执行成功了
- 但是接口响应还没返回给客户端，服务挂了
- 客户端超时后重试
- 这时 Redis key 还在，请求会被判定为重复请求

这种情况下：

- 从“防重复执行”角度看，没问题
- 但从“客户端拿不到成功结果”角度看，用户体验不好

更完整的幂等设计通常会做成：

- 记录请求状态
- 记录请求结果
- 重复请求时直接返回上次结果

而不是简单地只存一个 `"1"`。

---

## 3. key 设计太简单可能有冲突风险

当前 key 是：

```java
idempotent:幂等号
```

如果不同接口恰好用了相同幂等号，可能相互影响。

更稳妥的做法通常是把这些信息也拼进去：

- 类名
- 方法名
- URI
- 业务类型
- 用户 ID

比如：

```java
idempotent:createOrder:user123:request456
```

这样冲突概率更低。

---

## 4. 只靠客户端传幂等号，有依赖

这套方案依赖客户端配合：

- 客户端必须生成唯一幂等号
- 并且重复请求时必须带同一个幂等号

如果客户端每次重试都重新生成一个新幂等号，那防重就失效了。

所以这个机制通常要求：

- 前后端有统一约定
- 或者由服务端生成幂等 token 给前端

---

## 5. `PARAMETER` 模式实现细节比较复杂

你代码里提到：

```java
getParameterValue(joinPoint, idempotent.key());
```

但真实实现时要注意：

- Java 运行时未必总能直接拿到参数名
- 需要编译时保留参数名，或者通过注解绑定
- 如果参数是对象，还可能要支持从对象字段里取值

所以这一块实际实现要比示例复杂一些。

---

## 6. 异常分类可能过于粗糙

```java
return !(e instanceof BusinessException);
```

这等于把异常简单分成：

- 业务异常
- 非业务异常

但实际生产中可能还要分得更细：

- 参数校验异常
- 可重试异常
- 不可重试异常
- 下游超时异常
- 限流异常

不同异常对应是否删除 key，不一定一样。

# 1. 为什么要有 `ProceedingJoinPoint joinPoint`

```java
public Object around(ProceedingJoinPoint joinPoint, Idempotent idempotent)
```

这里的 `joinPoint` 表示：

- 当前被 AOP 拦截到的那个方法
- 也就是“连接点”的运行时信息

它的作用非常重要，因为环绕通知要做的不只是“前置增强”，还要决定：

- 要不要放行原方法
- 什么时候执行原方法
- 能不能获取方法参数
- 能不能拿到目标对象、方法签名等信息

最关键的一点是：

```java
joinPoint.proceed();
```

这句就是：

- **执行原来的目标方法**

如果没有 `ProceedingJoinPoint`，你就没法在 `@Around` 里手动控制目标方法执行。

---

## 你可以把它理解成

AOP 拦截到方法后，会把“这个方法调用的上下文”交给你。

这个上下文里包含：

- 调用的是哪个方法
- 方法参数是什么
- 目标对象是谁
- 什么时候继续执行原方法

所以这里必须要 `joinPoint`。

---

# 2. 为什么是 `ProceedingJoinPoint`，不是普通 `JoinPoint`

因为你这里用的是：

```java
@Around
```

**环绕通知** 需要能“继续执行”目标方法，所以参数要用：

- `ProceedingJoinPoint`

它比普通的 `JoinPoint` 多一个核心能力：

```java
proceed()
```

也就是“放行执行原方法”。

如果只是前置通知 `@Before`，通常可以用：

- `JoinPoint`

但如果是 `@Around`，一般就要用：

- `ProceedingJoinPoint`

---

# 3. 为什么还要有 `Idempotent idempotent`

这个参数表示：

- 当前被拦截的方法上的 `@Idempotent` 注解实例

因为你的切点写的是：

```java
@Around("@annotation(idempotent)")
```

这个表达式的意思是：

- 拦截带有 `@Idempotent` 注解的方法
- 并且把这个注解对象绑定到参数 `idempotent` 上

所以 Spring AOP 执行到这里时，会自动把目标方法上的注解传进来。

这样你就可以直接写：

```java
idempotent.source()
idempotent.key()
idempotent.expireSeconds()
idempotent.message()
```

来读取注解配置。

---

# 4. 如果没有 `idempotent` 参数会怎样

如果你只写：

```java
public Object around(ProceedingJoinPoint joinPoint)
```

其实也能工作，但你就不能直接拿到注解对象。

那你就得自己通过反射去拿方法上的注解，比如：

- 先从 `joinPoint` 拿方法签名
- 再拿 Method
- 再 `method.getAnnotation(Idempotent.class)`

这样会更麻烦。

而现在这种写法：

```java
@Around("@annotation(idempotent)")

```

相当于 Spring 直接帮你把注解注入进来了，更方便。

- 幂等号来源 `source()`
