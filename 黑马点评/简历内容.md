# 防止超卖和一人一单

## 第一版
- 对于一人一单: 可以直接去数据库查询是否下过单. 如果有对应优惠券的订单ID, 那么就拒绝请求. 同时为了防止同一个用户重复下单, 要使用分布式锁
- 对于库存超卖: 在更新的时候加上 ` where stock > 0`保证不超卖
- 但是该方案高并发下所有请求会直接打到数据库, 而且大量的数据库查询请求和更新数据以及锁竞争都集中在数据库, 严重影响秒杀业务的性能
## 第二版
- 然后因为我当前项目使用了Redis, 而Redis是基于内存的, 读取速度很快, 我就想着能否把下单资格的校验放到Redis中完成, 正好Redis有Lua脚本, 执行是原子性的, 满足我的要求
- 所以秒杀流程的最终优化: 
	- 我这个优化为, 核心使用 `Lua脚本进行资格校验 + Kafka异步下单`, 
	- 因为扣减库存, 生产订单, 这些步骤都是对MySQL进行操作, 但是实际上对于秒杀来说, 当判断你有秒杀资格的那一步起, 你就秒杀成功了, 剩下的步骤就是为了实现秒杀, 所以完全可以异步来执行, 提高性能
	- 流程: 
		- **资格判断**: 当用户请求进来以后, 先查秒杀券是否存在, 是否在秒杀券活动的时间内,  判断用户有无参与资格, 然后就执行Redis的Lua脚本, 原子的判断库存是否充足, 用户是否下过单等等, 通过的话, 就直接在Redis里预扣库存并且把用户写入下单集合, 标记占用资格.  然后生成一个全局订单ID, 然后立即发送Kafka消息(`包含 orderId、userId 和 voucherId`), 接口迅速返回
		- **异步处理**: Kafka消费者去执行数据库库存扣减和订单创建.   
			- 在消费者端, 我做了两层防护,  (**消费者端做幂等, 经过下面两层保证, 即使重复消费了消息, 也不会重复生成订单**)
				- 一层是先按userId加Redisson锁, 防止同一个用户并发消费,
				- 另一层是在**事务里**再次校验**数据库是否已经下单**, 并且用`where 库存 > 0`的条件更新兜底防超卖, 扣库存成功, 才保存订单. 
			- 这样在数据库层还有一次兜底, 保证不超买, 不生产重复订单
		- **失败补偿**: 
			- 如果Kafka发送失败, 或者消费过程失败, 我会执行Redis回滚脚本, 把预扣的库存和用户资格释放掉, 避免Redis与数据库结果不一致
	- 追问: 
		- **面试官如果问“你这里的下单资格是什么”**: 
		- 你可以直接说：
		- 我这里的下单资格有三层含义：
			1. 活动时间上有资格，也就是当前时间在秒杀开始和结束时间之间
			2. 库存上有资格，也就是 Redis 里的秒杀库存还大于 0
			3. 用户维度上有资格，也就是这个用户还没有抢过这个券
		- 只有这三个条件都满足，我才允许发送 Kafka 下单消息。

# 缓存优化
## 缓存击穿
- 对于缓存击穿, 它是热点key过期问题, 我想到了两种方案, 分别是 `互斥锁` 和 `使用逻辑过期`
- 互斥锁: 
	- 它是当大量请求访问数据库时, 给一个请求加锁去重建缓存, 其他请求阻塞
	- 因为锁竞争, 所以会一定程度上影响性能, 外界表现为不可用, 但是它保证了强一致性, 同时读取到的数据也是最新的
- 逻辑过期: 
	- 它就是对于热点数据不设置TTL, 而是设置一个逻辑过期时间
	- 当请求到来时, 获取key时会检查时间字段, 判断是否过期. 如果过期, 就让一个线程去加锁更新缓存, 其他请求先返回旧值
	- 它因为可以返回旧数据, 线程无需等待, 所以性能较好, 同时也保证了服务的可用性, 但是无法保证数据一致性
- 因为这是我觉得这算是一个社交类型的数据, 对于一致性没有那么高的要求, 暂时的旧信息可以接受, 所以选择了逻辑过期方案
- 测试: 我手动修改数据库数据, 使得数据不一致, 然后使用逻辑过期的情况下, 用Jmeter进行压力测试时, 4s 内 4000个线程的QPS是1000, 查看日志可以看到只有一次查询数据库重建缓存的过程
## 缓存穿透
- 对于缓存穿透, 它是有大量恶意请求, 使用数据库不存在的商铺ID去查询, 导致请求直接打到数据库的问题, 我想到的方案有 `缓存空值` 和 `布隆过滤器`

# 数据一致性
- [Redis](../面渣/Redis.md)可以看Redis中如何保证 MySQL和Redis一致性部分
- 我保证的是缓存和数据库的最终一致性, 因为店铺的信息一般读多写少
- 流程为 `先更新MySQL再删Redis + Kafka补偿重试`
- 当用户修改店铺信息时, 我会先在事务里更新数据库, 然后再删除对应店铺的缓存. 如果删除成功, 那么后续请求会从数据库中查询到最新值重建缓存; 如果删除失败, 那么就会把删除动作封装为一个Kafka消息发送出去, 里面包含缓存 key 和 重试次数. 消费者收到消息后会重试删除, 如果重试超出次数那么就记录错误日志并且人工介入

# Kafka
## 消息不重复消费
- 通过秒杀流程里的异步处理阶段, 在消费者端做幂等
- 还能咋样保证呢?
	- 生产者端可以开启生产者幂等, 使 `enable.idempotence=true` 和 重试机制, 防止重复写入
## 消息不丢失
- 做了两层配置: 
	- 第一层生产者端设置了 `acks=all`, 只要所有ISR副本全部同步成功之后才算发送成功
	- 第二层就是失败补偿, 即 Redis回滚
- 还可以咋样保证呢? 
	- 消费者端可以改为手动提交offset, 保证不少消费
