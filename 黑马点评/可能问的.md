**一、秒杀链路追问**

1. 你为什么要用 Redis + Lua，而不是直接数据库扣库存？

可能追问：

- Redis 为什么快？
- Lua 为什么能保证原子性？
- Redis 单线程是不是一定不会有并发问题？
- Lua 脚本执行期间会不会阻塞 Redis？
- 如果 Lua 脚本执行很慢会怎么样？

对应八股：

- Redis 单线程模型
- Redis IO 多路复用
- Lua 脚本原子性
- Redis 命令执行模型
- Redis 慢查询、big key、阻塞风险

推荐回答方向：

- 数据库直接抗秒杀流量压力大。
- Redis 先做资格过滤，把大量无效请求挡在数据库外。
- Lua 把“查库存、判断是否重复下单、扣库存、记录用户资格”合成一个原子操作，避免并发下超卖和重复资格占用。
- 但 Lua 不能写复杂耗时逻辑，否则会阻塞 Redis。

2. 你说 Redis 预扣库存，那数据库库存和 Redis 库存不一致怎么办？

可能追问：

- Redis 扣成功，Kafka 发送失败怎么办？
- Kafka 发送成功，但消费者失败怎么办？
- 数据库扣库存失败怎么办？
- Redis 回滚失败怎么办？
- 最终一致性和强一致性有什么区别？

对应八股：

- 分布式事务
- 最终一致性
- 补偿事务
- 本地消息表
- TCC / Saga / MQ 事务消息
- 幂等性

推荐回答方向：

- 这个项目没有追求强一致性，而是通过补偿保证最终一致性。
- Kafka 发送失败时回滚 Redis。
- 消费失败重试，超过阈值发死信队列并回滚 Redis。
- 数据库仍然用 `stock > 0` 做最后兜底。
- 如果 Redis 回滚失败，就需要日志告警、人工修复，或者进一步设计补偿任务扫描异常状态。

3. 为什么已经 Redis 判断一人一单了，数据库还要查一次？

可能追问：

- Kafka 为什么会重复消费？
- Redisson 锁能不能完全替代数据库幂等？
- 如果锁失效了怎么办？
- 数据库层怎么防重复？
- 是否应该加唯一索引？

对应八股：

- Kafka 至少一次投递
- 幂等设计
- 分布式锁
- 数据库唯一索引
- 乐观锁
- 悲观锁

推荐回答方向：

- Redis 是第一层过滤，不是最终事实源。
- Kafka 可能重复投递。
- Redisson 锁只能防并发，不能防历史重复消息。
- 数据库二次查询是业务幂等兜底。
- 更严谨的生产方案会在 `(user_id, voucher_id)` 上建唯一索引，数据库层强约束一人一单。

4. 你这里为什么用 Redisson 锁？不用 synchronized 可以吗？

可能追问：

- synchronized 和 ReentrantLock 区别？
- synchronized 在分布式场景为什么不行？
- Redisson 锁底层怎么实现？
- Redisson 看门狗是什么？
- 如果业务执行时间超过锁过期时间怎么办？
- Redis 分布式锁有什么问题？

对应八股：

- JVM 锁
- synchronized 原理
- ReentrantLock
- Redis `SET NX EX`
- Redisson watchdog
- 分布式锁误删问题
- Lua 解锁

推荐回答方向：

- 单机可以用 synchronized，但项目是 Web 应用，未来可能多实例部署，JVM 锁只能锁本进程。
- Redisson 基于 Redis 实现跨实例锁。
- Redisson 默认有 watchdog 自动续期，避免业务没执行完锁过期。
- 释放锁时要校验锁归属，避免误删别人的锁。

5. 你说用 `where stock > 0` 防止超卖，它是怎么防的？

可能追问：

- 这是乐观锁还是悲观锁？
- MySQL 更新时会加什么锁？
- 高并发下两个线程同时执行会不会都成功？
- `stock = stock - 1 where stock > 0` 为什么是原子的？
- MySQL 的行锁什么时候生效？

对应八股：

- MySQL 行锁
- InnoDB MVCC
- 当前读和快照读
- 乐观锁思想
- update 原子性
- 事务隔离级别

推荐回答方向：

- `update tb_seckill_voucher set stock = stock - 1 where voucher_id = ? and stock > 0` 是数据库层的原子更新。
- InnoDB 会对命中的记录加行锁。
- 并发更新会串行化执行，后续线程会基于最新库存判断 `stock > 0`。
- 所以库存为 0 后，更新失败，不会超卖。

推荐回答方向：

- 消息处理成功但提交 offset 前宕机，恢复后可能再次消费。
- 所以消费者必须幂等。

9. 你说按 `userId` 作为 Kafka key 保证顺序，具体怎么保证？

可能追问：

- Kafka 顺序性是全局有序还是分区有序？
- 相同 key 一定到同一个 partition 吗？
- 如果 partition 数变化会怎样？
- 多消费者会不会破坏顺序？
- 一个 partition 能被多个消费者同时消费吗？

对应八股：

- Kafka 分区机制
- key 分区策略
- 分区内有序
- Consumer Group 消费模型
- Rebalance

推荐回答方向：

- Kafka 只保证单个 partition 内有序。
- 使用 `userId` 作为 key，相同用户的消息会路由到同一 partition。
- 一个 partition 在同一个消费组里同一时刻只会被一个消费者消费，所以同用户消息顺序可以保证。
- 但如果调整 partition 数，key 到 partition 的映射可能变化，顺序保证要谨慎。

11. 逻辑过期为什么可以防击穿？

可能追问：

推荐回答方向：

- 逻辑过期不会让热点 key 直接失效。

**四、缓存一致性追问**

14. 为什么是先更新数据库再删缓存？为什么不是先删缓存再更新数据库？

可能追问：

- 先删缓存再更新数据库有什么问题？
- 先更新数据库再删缓存还有没有问题？
- 延迟双删是什么？
- 事务提交前删缓存有什么问题？
- 你为什么改成事务提交后删缓存？

对应八股：

- Cache Aside Pattern
- 缓存一致性
- 延迟双删
- 事务同步回调
- 最终一致性

推荐回答方向：

- 先删缓存再更新 DB，可能出现读请求在 DB 更新前回填旧值。
- 先更新 DB 再删缓存，相对更稳。
- 但必须注意删缓存要在事务提交后，否则事务未提交时并发读仍可能读旧值并写回缓存。
- 所以当前项目改成事务提交后删除缓存。
- 删除失败则 Kafka 补偿。

**九、可能被挑战的点**

这些是面试官可能“挑刺”的地方，你要提前准备。

1. 你说保证不重复订单，但数据库没有唯一索引怎么办？

回答：

- 当前通过 Redis 资格 + Redisson 锁 + 数据库查询做了业务幂等。
- 但生产更严谨应该加 `(user_id, voucher_id)` 唯一索引，防止极端并发或代码缺陷导致重复写入。
- 我会把唯一索引作为最终防线。

2. 你说消息不丢，但消费者自动提交 offset，会不会丢？

回答：

- 自动提交 offset 确实存在风险，如果 offset 已提交但业务处理失败，可能造成消息丢失。
- 当前项目通过业务重试和补偿降低影响，但更可靠的方案是关闭自动提交，在业务处理成功后手动提交 offset。
- 对核心交易链路，手动提交更稳。

3. Redis 预扣库存后，数据库扣库存失败，怎么处理？

回答：

- 消费失败会进入重试，超过阈值后发送死信并回滚 Redis。
- 数据库也用 `stock > 0` 兜底。
- 如果回滚失败，需要补偿任务或人工处理，这属于最终一致性方案的兜底。

4. 你用 Spring Task，多台机器部署会不会重复执行？

回答：

- 当前单体单实例场景下可以。
- 如果多实例部署，需要分布式锁控制只有一个实例执行，或者使用 XXL-JOB 这类分布式调度平台。
- 即使重复执行，SQL 的状态条件也能保证不会重复回补库存。

5. 逻辑过期返回旧数据，用户看到旧数据怎么办？

回答：

- 这是高可用和一致性的取舍。
- 店铺信息读多写少，对短暂旧数据容忍度较高。
- 对强一致数据，例如库存、余额、订单状态，不能用这种方式做最终判断。

**十一、面试官可能让你画流程**

你要能画出这几个流程：

1. 秒杀请求流程： 用户请求 → 查秒杀券 → 时间校验 → Redis 库存 Key 兜底回填 → Lua 校验库存和一人一单 → Redis 预扣库存 + Hash 记录资格 → 发送 Kafka → 返回订单 ID → 消费者加 Redisson 锁 → DB 二次校验 → DB 扣库存 → 创建未支付订单。
    
2. Kafka 失败补偿流程： 发送失败 → 重试 → 失败超过阈值 → Lua 回滚 Redis。 消费失败 → 重发重试消息 → 超过阈值 → 死信队列 → Lua 回滚 Redis。
    
3. 店铺缓存一致性流程： 读缓存 → 命中且未逻辑过期直接返回 → 逻辑过期则异步重建。 更新店铺 → 事务更新数据库 → 事务提交后删缓存 → 删除失败发 Kafka 补偿 → 补偿消费者重试删除。
    
4. 超时关单流程： Spring Task 每分钟扫描 → 查 30 分钟前未支付订单 → 每批 100 条 → 查订单当前状态 → `status=unpaid` 才取消 → 回补库存 → Redis 回滚资格 → 失败发 Kafka 补偿重试。
